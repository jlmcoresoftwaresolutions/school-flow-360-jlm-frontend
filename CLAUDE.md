## Comandos

- `bun install` — instala as dependências (lockfile é `bun.lock`)
- `bun run dev` — inicia o servidor de dev do Vite (abre o navegador automaticamente, ver `vite.config.ts`)
- `bun run dev:https` — o mesmo servidor em `https` (certificado autoassinado do `@vitejs/plugin-basic-ssl`) e aberto na rede, para entrar de outro aparelho (`https://<ip-da-máquina>:5173`): por `http` no IP da rede o navegador não guarda a sessão e o login recusa. Na primeira visita o navegador pede para aceitar o certificado. Fica desligado no `bun run dev` e no E2E
- `bun run build` — checa os tipos (`tsc -b`) e depois faz o build de produção
- `bun run preview` — faz o preview local do build de produção
- `bun run lint` / `bun run lint:fix` — executa o ESLint (flat config em `eslint.config.js`)
- `bun run format` / `bun run format:check` — Prettier em modo write/check
- `bun run storybook` — executa o Storybook localmente na porta 6006 (documentação de componentes)
- `bun run build-storybook` — gera o site estático do Storybook em `storybook-static/` (ignorado pelo git)
- `bun run test` — executa a suíte do Vitest uma vez (`vitest run`)
- `bun run test:watch` — executa o Vitest em modo watch
- Para rodar um único arquivo de teste: `bunx vitest run src/ds-components/atoms/Text/Text.test.tsx` (ou remova o `run` para modo watch apenas nesse arquivo)
- `bun run e2e` — executa a suíte E2E do Playwright (`playwright test`) contra `e2e/`, ver a seção sobre Playwright abaixo. Numa máquina nova, rode antes `bunx playwright install chromium` uma vez: o navegador do Playwright é baixado à parte, não vem pelo `bun install`

**Não reinstale `@storybook/addon-vitest` ou `@chromatic-com/storybook`** — o `storybook init` os adiciona por padrão, mas foram removidos deliberadamente (ver a seção sobre Storybook abaixo). Os testes unitários deste projeto usam uma configuração simples e independente do Vitest, propositalmente não integrada ao Storybook.

Para checar tipos sem fazer build: `bunx tsc -b --noEmit` (o projeto usa TS project references — `tsconfig.app.json` para `src/`, `tsconfig.node.json` para a configuração do Vite).

## Arquitetura

Esta é uma aplicação React 19 + TypeScript + Vite, construída do zero sobre uma camada customizada de design tokens em `src/foundation/`. A estilização é feita com `styled-components` (sem arquivos CSS puros) — o reset global que antes ficava em `index.css` agora é `src/styles/GlobalStyle.ts`, um `createGlobalStyle`, renderizado uma única vez em `main.tsx` junto com o router.

### Roteamento

`src/routes/routes.tsx` (reexportado via `src/routes/index.ts`, então é importado como `from "./routes"`/`from "@/routes"`) é a fonte única das definições de rota, exportando um `router` construído com o `createBrowserRouter` do `react-router-dom`: entradas de topo `{ element, path }` (ex.: `/login`) convivem com uma rota de layout `{ element: <AppShell />, children: [{ element, path }, ...] }` que envolve as páginas autenticadas em `AppShell` (`src/ds-components/templates/AppShell`, o template que compõe `Sidebar` + área de conteúdo via `<Outlet />` do `react-router-dom`). `main.tsx` renderiza `<RouterProvider router={router} />` (não existe `App.tsx` — esse placeholder foi substituído por `src/pages/` assim que o roteamento entrou). Cada página (e o próprio `AppShell`) é carregada sob demanda pela propriedade `lazy` da rota (`lazy: async () => { const { Login } = await import("@/pages/Login"); return { Component: Login } }`), o que faz de cada uma um chunk próprio: abrir `/login` não baixa os seletores de data/cor do Minha Organização. **Importe a página da própria pasta (`@/pages/Login`), nunca do barrel `@/pages`** — o barrel puxaria todas as páginas para o mesmo chunk. As rotas de topo com `lazy` recebem `hydrateFallbackElement: <GlobalLoading visible />`, o overlay mostrado enquanto o chunk da primeira rota chega. O `"sideEffects": ["./src/main.tsx"]` do `package.json` é o que deixa o bundler descartar, de cada chunk, os módulos não usados dos barrels de `src/ds-components/` (sem ele, importar o `Input` de `@/ds-components/molecules` arrastaria o `DateInput`/`ColorPicker`/MUI junto); mantenha-o assim e não crie módulos que dependam de ser importados só pelo efeito colateral (`import "./algo"`) — se precisar, inclua o arquivo nessa lista. **O acesso é decidido pelos `loader`s das rotas, antes de qualquer render:** a rota de layout do `AppShell` (todas as páginas atrás do login) redireciona para `/login` quem não tem sessão (`getSessionState()`, ver `src/utils/session/`), levando a página pedida em `?redirect=` e, se a sessão acabou de vencer, `?expired=1` (o login mostra o aviso e, depois de entrar, volta para essa página — só caminhos internos, ver `getSafeRedirectPath` em `src/utils/authRedirect/`; a volta passa de novo pelo mesmo `loader`, então uma página que deixou de ser permitida continua fechada), `/login` e `/forgot-password` (as páginas de entrada) redirecionam para a home quem já tem (`/reset-password` e `/accept-invitation`, abertas pelos links dos e-mails, não: o link continua valendo mesmo num navegador com alguém logado), e um `path: "*"` final manda qualquer endereço desconhecido para `/login`. **O loader do `AppShell` roda a cada troca de página** (`shouldRevalidate`): renova uma sessão cujo token de acesso venceu (e manda ao login com `?expired=1` a que o backend não renova), lê quem entrou (o `context` guardado com a sessão, relido do `/api/me` uma vez por visita) e manda para `/access-denied` (`paths.accessDenied`, página `AccessDenied`, JLM-181) quem abre uma página que os seus papéis não abrem: ela diz que a página não está disponível, sem contar nada sobre a página pedida, distinta de uma falha técnica, e oferece voltar ao início. Quem pode abrir cada página fica em `pageRoles` (`src/routes/access.ts`, pela chave de `paths`; a regra em `canOpenPage`, de `@/utils/access`): uma página fora dali abre para qualquer pessoa logada, só até a Matriz v2.0 (JLM-208) definir as dos outros papéis. O menu esconde o que o papel não abre, e um grupo vazio some; nada disso substitui a checagem do backend em toda chamada. O dado do loader é o `UserContext`, que o `AppShell` mostra no topo. Uma página nova atrás do login entra como filha do `AppShell` e já herda essa proteção. **Todo item do menu lateral tem a sua página** (hoje em branco, exceto o Minha Organização, em `src/pages/<Nome>/`, ex.: `Classes`, `Tuition`), e a chave de cada uma em `paths.ts` é a mesma chave do menu (`shell.nav`, ex.: `classes` → `/academic/classes`): o `AppShell` monta o menu a partir de `menuGroups`/`bottomGroups` (grupo → chaves das páginas) e acha o caminho, o item ativo e o breadcrumb (grupo → página) por essa chave. Um item novo no menu é a chave em `shell.nav`, o caminho em `paths.ts`, a rota em `routes.tsx` e a página. Os caminhos ficam em `src/routes/paths.ts` (`paths` e `homePath`, para onde o usuário vai depois do login); importe-os direto de `@/routes/paths`, nunca escreva o caminho literal em outro lugar, e não importe o `router` numa página. **As URLs das páginas são sempre em inglês** (`/forgot-password`, `/administration/my-organization`), mesmo com a interface em pt-BR: o texto na tela é traduzido, o endereço não. Uma página nova ganha um caminho em inglês em `paths.ts`, e a chave e a página também têm nome em inglês (ex.: `myOrganization` → `/administration/my-organization`, página `MyOrganization`), ainda que o item do menu se chame "Minha Organização". **A Minha Organização (`MyOrganization`, `paths.myOrganization`) se chamava Minha Unidade** até 2026-11-24, quando passou a mostrar a rede inteira com todas as unidades: o endereço antigo (`paths.legacyMyUnit`, `/administration/my-unit`) só redireciona para o novo, para links e favoritos antigos continuarem valendo. Um `<Link>` é renderizado via a prop polimórfica `as` do `Text` (`<Text as={Link} to="/rota">`) em vez de uma `<a>` crua, do mesmo jeito que qualquer outro alvo de `as`.

### Formulários com alterações não salvas

**Toda página atrás do login avisa antes de sair de um formulário com alterações não salvas.** O `AppShell` envolve o topo e as páginas em `UnsavedChangesGuard` (`src/components/UnsavedChangesGuard/`), que usa o `useBlocker` do `react-router-dom` (por isso exige o router de dados — `createBrowserRouter` no app, `createMemoryRouter` em testes/stories, nunca `MemoryRouter`): enquanto algum formulário reportar alterações, qualquer navegação que mude o caminho ou a query (menu, links, voltar do navegador, "Sair") para num `ConfirmDialog` centralizado ("Descartar alterações?" — "Continuar editando" / "Sair sem salvar"). Recarregar ou fechar a aba só pode ganhar o aviso nativo do navegador (`beforeunload`); nenhum site pode trocá-lo por um modal próprio. **Um formulário novo atrás do login deve chamar `useUnsavedChanges(temAlteracoes)`** (de `@/components`), com "tem alterações" = está editando **e** o rascunho difere do original (ex.: `isEditing && !isShallowEqual(draft, original)`, com `isShallowEqual` de `@/utils/objects`) — só abrir a edição sem mudar nada não avisa. Ver os dois cartões de `MyOrganization.tsx`. Como o `GlobalLoading`, o guarda é casca do app e traduz o próprio texto (chave `unsavedChanges`).

### Login, limite de sessões e ativação por convite

**O login aceita o e-mail ou o apelido** (`login` no corpo de `POST /api/auth/login`): toda conta tem um apelido único no tenant (3 a 60 letras, números, `.`, `_` ou `-`), e um aluno sem e-mail entra só por ele. O `/api/me`, o contexto do login e as views de usuário trazem o `nickname` (sempre presente) e o `email` (nulo para quem só tem apelido): o detalhe do usuário e o Meu perfil mostram o apelido, e onde a tela nomeia uma pessoa usa `getPersonName` (`src/pages/shared/userAccess/personName.ts`: o nome, senão o e-mail, senão o apelido); o `PersonSummary` mostra o apelido no lugar do e-mail. O campo "E-mail ou apelido" confere o formato antes de enviar (com `@`, um e-mail; sem, um apelido), e a espera depois de senhas erradas vale para o que foi digitado. **Senha temporária**: o Admin, ou a Secretaria para quem está só nas suas unidades, gera uma pelo menu de ações do detalhe do usuário (`TemporaryPasswordDialog`, `POST /api/users/{id}/temporary-password`, oferecida só quando o detalhe traz `TEMPORARY_PASSWORD` em `eligibleActions`; nunca na própria conta). Ela aparece uma única vez, com "Copiar senha", vale 7 dias e encerra as sessões da pessoa. Quem entra com ela tem `context.mustChangePassword`, e até trocá-la o backend responde 403 `PASSWORD_CHANGE_REQUIRED` a tudo menos `GET /api/me`, a troca e o logout: o loader do `AppShell` manda para `/change-password` (`paths.changePassword`, página `ChangePassword`, fora do `AppShell`, com `?redirect=` da página pedida), e o `httpClient` também, a partir do 403 (`requirePasswordChange`, de `src/utils/authRedirect/`). A página de troca sempre relê `/api/me` para saber se a troca ainda é necessária, nunca o contexto guardado, para não ficar indo e voltando entre ela e a página recusada; trocar (`changeMyPassword`, `POST /api/me/password`) atualiza o contexto e segue para a página pedida, e "Sair" é a outra saída. O mesmo formulário (`src/pages/shared/password/`: `usePasswordChange` e `PasswordChangeFields`) troca a senha a qualquer hora pelo Meu perfil, num modal. As recusas ficam no campo: `CURRENT_PASSWORD_INVALID`, `PASSWORD_UNCHANGED`, `PASSWORD_INVALID` (12 a 128 caracteres).

**Ninguém se cadastra pelo login**: uma conta nasce de um convite (ou do cadastro manual, que é o mesmo convite), e a pessoa cria a própria senha em `/accept-invitation?token=...&tenant=...` (`src/pages/AcceptInvitation/`), o link que o backend manda por e-mail. A página valida o link antes de mostrar o formulário (qualquer link morto é o mesmo 404 `INVITATION_INVALID`), mostra a instituição e o acesso que o convite dá (papéis e unidades, que não aparecem para edição), pede nome (obrigatório: toda conta tem nome; o do convite vem preenchido, e o digitado o substitui), telefone (opcional, idem; o do convite não é reenviado) e a senha, manda as duas chamadas para o tenant do link e trata cada recusa do aceite pelo `code` (`INVITATION_EXPIRED`, `INVITATION_ALREADY_USED`, `USER_DUPLICATE`, `UNIT_INACTIVE`, `WEAK_PASSWORD`, `NAME_REQUIRED`, `TERMS_NOT_ACCEPTED`). **Os Termos de Uso e o Aviso de Privacidade são obrigatórios** (JLM-145): uma caixa de aceite com a versão vigente (`termsVersion`, do `validate`), enviada de volta no aceite; se a versão mudou com o formulário aberto (`TERMS_VERSION_INVALID`), a página relê o convite, desmarca a caixa e pede o aceite de novo, sem perder o que foi digitado. Os links dos Termos e do Aviso de Privacidade vêm do `validate` (`termsUrl`/`privacyUrl`), nulos até os textos finais serem publicados: cada um aparece abaixo da caixa (fora do rótulo, em nova aba) só quando vier preenchido. **Senha errada, conta inativa ou bloqueada e conta sem papel ativo recebem do backend o mesmo 401 sem `code`**, de propósito (não revela se a conta existe), e o login mostra uma só mensagem genérica, que manda falar com a secretaria. **No login, com 5 sessões abertas** o backend recusa a 6ª com um 409 `SESSION_LIMIT_REACHED` que traz um desafio (5 minutos, uso único) e as sessões da pessoa; o `SessionLimitDialog` (`src/pages/Login/`) as lista (navegador e sistema, via `summarizeUserAgent`, e quando começou) e "Encerrar e continuar" encerra a escolhida e entra no mesmo passo (`replaceSessionAtLimit`). Uma sessão que já tinha sido encerrada sai da lista; um desafio vencido volta ao login com aviso.

### Usuários e convites (P02)

As páginas **Lista de usuários** (`src/pages/UserList/`) e **Convites** (`src/pages/Invites/`) leem o backend página a página (`listUsers`/`listInvitations`, com `{ showLoading: false }`: a tabela mostra o próprio carregamento), com busca (`useDebouncedValue`) e filtros que voltam à primeira página. Cada resposta é guardada com a chave da consulta que a pediu, então trocar um filtro esvazia a tabela na hora e nunca mostra dados de outro contexto; uma instituição sem registros, uma busca sem resultado, uma falha e uma recusa (403) aparecem cada uma de um jeito. O que as duas dividem fica em `src/pages/shared/userAccess/`:

- `useUnitDirectory`: as unidades de quem entrou, lidas do backend (`listSchoolUnits`): um Admin recebe todas; uma Secretaria, só as atribuídas a ela (JLM-2/128), cada uma com a situação, para uma unidade inativa nunca ser oferecida.
- `useAccessLabels`: papel numa unidade ("Secretaria · Unidade Centro", Admin = "Toda a instituição"; uma unidade inativa ganha "(inativa)", pelo `unitStatus` que cada atribuição traz ou pelas unidades conhecidas), situações, origem e datas.
- `NewAccessModal`: convidar e cadastrar manualmente, o mesmo formulário e, no backend, o mesmo convite de 48 h (o manual com `origin=MANUAL`), sem senha. Os papéis oferecidos vêm de `getGrantableRoles` (Admin: todos; Secretaria: todos menos Admin, só nas suas unidades ativas, e nunca para mudar o próprio acesso), sem nenhum ajuste de permissão por pessoa. Antes de enviar, uma revisão mostra destinatário, papéis e unidades. Cada revisão gera um `Idempotency-Key`: repetir depois de uma falta de resposta devolve o mesmo convite. Uma recusa sobre os dados volta ao formulário com o campo marcado (`USER_DUPLICATE`, `INVITATION_PENDING`, `ROLE_NOT_GRANTABLE`, `UNIT_INACTIVE`).
- `PersonSummary`: o nome sobre o e-mail numa linha de tabela.

O detalhe do usuário (`UserDetailsModal`) relê o usuário ao abrir: dados, papéis e unidades ativos, o que cada papel permite (só informativo) e os acessos revogados. **Do menu de ações no cabeçalho do detalhe (`ActionMenu` pequeno, passado ao `Modal` pela prop `headerAction`, antes do X) abrem as ações que o backend permite** (`eligibleActions`; o aviso da própria conta fica no corpo), cada uma no próprio diálogo, controlado pela `UserList`: editar nome e telefone (`EDIT_PROFILE`, `ProfileModal`, com o `version`), alterar papéis e unidades (`AssignmentsModal`: o acesso atual com "Remover"/"Manter", o que está fora do alcance da Secretaria travado e devolvido intacto, já que o backend substitui o conjunto inteiro, e papéis novos pelo `AssignmentFields`; antes de salvar, uma revisão com o `AccessChangeSummary`, que mostra o que entra, sai e continua e o que muda no alcance, avisa a concessão de Admin e pede confirmação explícita numa redução; ao menos um papel fica, e tirar tudo é a revogação), revogar acesso (`RevokeModal`: escolhe os papéis, revisa e confirma; sem nenhum papel a pessoa não entra, mas a conta não é inativada nem apagada), gerar uma senha temporária (`TemporaryPasswordDialog`, ver "Login") e inativar ou reativar a conta (`AccountStatusDialog`). Toda mudança de acesso encerra as sessões da pessoa. **Ninguém altera o próprio acesso** (matriz ACC-M09): na própria conta só aparece "Editar dados". O backend já manda só `EDIT_PROFILE` na própria conta de quem não é Admin, mas ainda oferece ao Admin as ações de acesso na própria conta (decisão pendente com o Lucas); a tela as esconde para todos. As recusas são lidas pelo `code` em `useUserActionErrors` (`VERSION_CONFLICT` relê o usuário e mantém o que foi feito, `LAST_ADMIN`, `SCOPE_DENIED`, `NO_ACTIVE_ASSIGNMENT`...). Depois de uma ação, a lista é relida e o detalhe reabre. Um convite só pode ser reenviado se estiver pendente ou vencido, e cancelado se estiver pendente; os dois pedem confirmação e releem a lista. Quem entrou é lido em qualquer página atrás do login com `useSignedInUser` (de `@/hooks`), o dado do loader da rota do `AppShell` (`shellRouteId`, de `@/routes/paths`). Cobertos pelo E2E (`e2e/users.spec.ts`, `e2e/invites.spec.ts`, `e2e/user-actions.spec.ts`, com o backend simulado em `e2e/support/userAccess.ts`).

### Conta, sessões e auditoria (P02)

- **Meu perfil** (`/account/profile`, `paths.myProfile`, página `MyProfile`, fora do menu lateral) abre pelo menu do usuário no topo (`userMenuItems` do `AppShell`): nome e telefone lidos de `GET /api/me` e editados no lugar (`updateMyProfile`, com o `version`), e o acesso da pessoa só para leitura. Salvar atualiza o `context` guardado na sessão (`updateSessionContext`) e revalida o loader (`useRevalidator`), para o nome do topo mudar na hora. Um último cartão troca a própria senha num modal (`ChangePasswordModal`, com a senha atual).
- **Sessões ativas** (`ActiveSessions`, matriz ACC-M10): as sessões da própria pessoa (`listMySessions`), com o aparelho resumido do user agent, a atual marcada e "Encerrar sessão" nas outras (`endMySession`, com confirmação; `SESSION_NOT_FOUND` = já encerrada). A atual se encerra com "Sair".
- **Auditoria** (`Audit`, só Admin, JLM-197): os eventos ficam guardados por 5 anos, imutáveis no banco (backend `43ef09e`, V38; o Histórico de pessoas lê a mesma tabela, então também guarda 5 anos), e a tela diz isso. `listAccessAuditEvents` página a página, com período (padrão 30 dias, até 366, validado na tela), autor (a lista de usuários), unidade, tipo de evento e resultado. Os tipos de evento conhecidos ficam em `Audit/auditEvents.ts` (ação + tipo de entidade → rótulo); um evento desconhecido aparece com os códigos. Uma alteração mostra só os nomes dos campos (`details`), nunca valores. Login, logout, sessão encerrada e limite de sessões (substituída e atingido, este como negado) chegam a `/api/audit` desde o backend `cd00e52`; a renovação de sessão e eventos sem autor conhecido ficam só na tabela de segurança do backend. O alvo de um evento de sessão aparece só como "Sessão", sem o id.

### Pessoas: alunos e responsáveis (P03)

O contrato é o `docs/P03_CONTRATO.md` do backend (conferido no `b810438`), com as regras PE-01 a PE-43 do `sfback-basis.md`. **Só Admin e Secretaria abrem as telas de pessoas** (PE-14, `pageRoles` de `students`/`guardians`); a Secretaria vê só as suas unidades, e uma pessoa fora do alcance responde 404 `PERSON_NOT_FOUND`, igual a inexistente. Alunos (`/administration/students`, página `Students`) e Responsáveis (`/administration/guardians`, página `Guardians`) ficam no grupo Administração do menu (o menu tem só dois níveis, então não há um nível "Pessoas"; o vínculo abre a partir do aluno, e o backend não tem lista de vínculos). Uma página de um registro abaixo do caminho de uma página (`/administration/students/12`) herda a regra de acesso dela (`getPageKey` procura o caminho pai). As listas leem `listStudents`/`listGuardians` página a página, como a Lista de usuários, pelo `usePeopleList` (`src/pages/shared/people/`), que descarta a resposta de uma consulta antiga e separa recusa (403), falha e **limite de buscas**: as listas e a pesquisa de pessoas dividem o limite de 30 por minuto por pessoa (429 `SEARCH_RATE_LIMITED`), mostrado pelo `PeopleListError` como um estado próprio. A situação do cadastro (Rascunho, Ativo, Inativo) vem do `usePeopleLabels`. **Pesquisar pessoas** (`/administration/people-search`, página `PeopleSearch`, P03-S01) é a pesquisa global antes de cadastrar (`searchPeople`): não lê nada até um termo ser pesquisado (botão ou Enter; nome, documento, e-mail, apelido ou código do aluno), os filtros (tipo, situação, unidade) e as páginas repetem o mesmo termo, e cada linha mostra os cadastros da pessoa (aluno e/ou responsável, cada um com a sua situação) e o que coincidiu (`matchedBy`). Ela só encontra quem está no alcance de quem pesquisa, então "ninguém encontrado" nunca afirma que a pessoa não existe na instituição; a checagem exata em todas as unidades (`checkPerson`) e a revisão de duplicidade entram com o cadastro, que é quem as usa. **Cadastro e Perfil 360 do aluno** (P03-S03/S04): `StudentForm` (`/administration/students/new` e `/administration/students/:studentId/edit`, `paths.studentNew`/`studentEdit`, montados com `generatePath`) e `StudentProfile` (`/administration/students/:studentId`, `paths.studentProfile`). O formulário divide com o futuro do responsável os campos de pessoa (`src/pages/shared/people/`: `PersonFields`, com os limites do backend em `personForm.ts`, e o catálogo de documentos `useDocumentTypes`): identificação, contato, documento (tipo do catálogo e número juntos; na edição o número vem mascarado e em branco mantém o atual) e endereço (CEP com ViaCEP e UF), além da unidade de referência (só unidades ativas no alcance), do apelido (ao criar, em branco o backend sugere; na edição é obrigatório e só vai no corpo quando muda, pelo `toNicknameChange` de `personForm.ts`; sem e-mail de acesso, trocá-lo encerra as sessões da pessoa, o que o texto de ajuda avisa; `NICKNAME_IN_USE` e `NICKNAME_INVALID` ficam no campo) e da observação. O aluno nasce rascunho; as recusas do backend ficam no campo pelo `code`; um 409 `DUPLICATE_REVIEW_REQUIRED` abre o `DuplicateReviewDialog`, que abre a revisão com os mesmos dados que o backend confere (`toStudentSignals`: e-mail de contato, documento, nome com nascimento; na edição só e-mail e documento que mudaram), mostra cada candidato só com o que o operador pode ver (fora do alcance: nome parcial e identificadores mascarados, nunca aberto), e termina em "Abrir este cadastro" (decisão `REUSE`, registrada) ou "Manter separado" (com justificativa numa coincidência forte), que salva de novo com o `duplicateReviewId`; nada é mesclado. Um conflito de versão relê o aluno e mantém o que foi digitado; um cadastro sem resposta pede para conferir a lista antes de tentar de novo. Uma página que navega logo depois de salvar marca a navegação com `leavingAfterSave` (de `@/components`), que o `UnsavedChangesGuard` deixa passar. O perfil mostra as abas que o backend libera em `sections` (Dados e Responsáveis, este com os vínculos e os convites) e, no menu de ações, só o que a situação permite: editar, ativar/descartar (rascunho), inativar (ativo), reativar (inativo) e criar o acesso do aluno (ativo: a senha temporária do `TemporaryPasswordDialog`, de `shared/userAccess`, sobre o próprio usuário do aluno, que entra pelo apelido). Ativar ou reativar lista o que falta (`activationBlockers`) e fica bloqueado enquanto faltar algo, para todos. **Regra do responsável (DP-P03-02, decisão do Lucas, backend `acf8cbe`):**

- Um aluno menor de 18 anos só fica ativo com um responsável ativo vinculado, sem exceção para ninguém, Admin incluído. O `NO_GUARDIAN` só vem para menor.
- A idade é contada em anos completos pela data de nascimento; no dia do 18º aniversário a pessoa já é adulta, e ser aluno de EJA não muda nada.
- Com 18 anos ou mais, o aluno ativa sem responsável no fluxo normal, sem motivo.
- Não existe mais o motivo de exceção (`exceptionReason`, `ADMIN_EXCEPTION_ONLY`, `EXCEPTION_REASON_INVALID`). O `activatedByException` fica só como histórico.
- Não dá para encerrar o último vínculo de um aluno ativo menor (`LAST_GUARDIAN`), nem inativar o único responsável de um (o backend recusa a operação inteira). Com aluno adulto, as duas coisas podem.
- Uma data de nascimento que torne menor um aluno ativo, adulto e sem responsável é recusada no campo (422 `GUARDIAN_REQUIRED`).
- A tela só antecipa o aviso do último vínculo pelo `isMinor` de `shared/people/personAge.ts`; quem decide é o backend.

O `PUT` de aluno e de responsável substitui o formulário inteiro, então todo salvamento reenvia todos os campos. Um registro abaixo de uma página do menu mantém o item ativo e o breadcrumb dela. **Cadastro e detalhe do responsável** (P03-S06/S07): `GuardianForm` (`paths.guardianNew`/`guardianEdit`) e `GuardianProfile` (`paths.guardianProfile`), sobre os mesmos campos de pessoa, sinais de duplicidade (`toPersonSignals`), recusas por campo (`usePersonFieldErrors`) e revisão do aluno. O responsável nasce ativo na unidade escolhida (só ao criar; depois segue as unidades dos alunos, mostradas só para leitura), e a edição muda o apelido dele como a do aluno (bloco Acesso) e nunca ganha acesso, convite nem vínculo por aqui: o acesso dele é só o convite. O detalhe tem as abas Dados e Alunos (os vínculos com os alunos do alcance de quem consulta, o nome abrindo o perfil do aluno, e vice-versa na aba Responsáveis do aluno; as células do vínculo ficam em `shared/people/LinkCells`) e as ações editar, ativar (rascunho), inativar e reativar; inativar o único responsável de um aluno ativo menor de 18 anos é recusado (`LAST_GUARDIAN`) com a orientação de vincular outro antes. **Vínculos e convite do responsável** (P03-S08, JLM-244) ficam na aba Responsáveis do aluno (`StudentProfile/links/`; o backend não tem lista de vínculos): "Vincular responsável" (`NewLinkModal`) escolhe um responsável já cadastrado no `GuardianPicker`, que busca os do alcance (`listGuardians`; um inativo ou já vinculado aparece, mas não pode ser escolhido) e, recolhida, a conferência exata em todas as unidades por e-mail ou documento (`checkPerson`): fora do alcance vem só parte do nome e a prova de reuso, enviada como `reuseRef` no lugar do `guardianId`; ninguém é cadastrado ali. O vínculo leva o parentesco do catálogo (`useRelationshipTypes`, `/api/catalogs/relationship-types`), as três responsabilidades independentes (`LinkFields`: pedagógica, financeira, contato; o padrão é o do backend), o início (em branco, hoje) e a confirmação do consentimento do responsável (LGPD, obrigatória). Um vínculo ativo é editado (`EditLinkModal`, com o `version`; num conflito relê e mostra a versão atual, mantendo o que foi digitado) ou encerrado (`EndLinkDialog`: motivo obrigatório, fim em branco = hoje e nunca antes do início, o vínculo fica no histórico); o último responsável de um aluno ativo menor de 18 anos não pode ser encerrado por ninguém, e a tela orienta vincular outro antes; o de um adulto pode. "Convidar por e-mail" (`InviteGuardianModal`) manda o convite de acesso de 48 h com o parentesco e as responsabilidades propostos (um responsável já cadastrado e sem acesso é escolhido no mesmo seletor, para a conta ficar nele); depois do aceite o convite fica "Aguardando a escola confirmar" e o menu da linha confirma (cria o vínculo, com o consentimento do próprio responsável) ou recusa (`InvitationDecisionDialog`). Aluno inativo não ganha vínculo nem convite. Um responsável já vinculado ao aluno não aparece entre os convites, e convidá-lo é recusado no campo (409 `GUARDIAN_ALREADY_LINKED`); um vínculo manual liquida o convite aberto do mesmo responsável (backend `e482a3c`, RB-85). As recusas do backend vão para o campo ou o formulário por `useLinkErrors`; sem resposta, o perfil é relido antes de tentar de novo. **Documentos e histórico** (JLM-250) são abas do perfil do aluno e do detalhe do responsável, mostradas quando o backend as libera em `sections` (`DOCUMENTS`, `HISTORY`), com componentes divididos em `shared/people/documents/` e `shared/people/history/`. Documentos (`PersonDocuments`): tipo do catálogo, número mascarado, emissão, validade (só para tipo que tem), arquivo e a situação que o backend deriva (Válido, Sem arquivo, Vencido, Arquivado). "Novo documento" (`NewDocumentModal`) registra e, se escolhido, já envia o arquivo; se o envio falhar ou for cancelado, o documento fica registrado Sem arquivo e a mensagem diz por quê. Anexar ou substituir (`DocumentFileModal`) confere o arquivo antes de enviar (PDF, JPEG ou PNG, até 10 MB, `checkDocumentFile`) e mostra o progresso com "Cancelar envio" (`useDocumentUpload`, com `onUploadProgress` e `signal` do `RequestConfig`); cancelado, nada é guardado. Baixar pede um link de 5 minutos a cada vez e o abre numa nova aba, sem guardá-lo; arquivar (`ArchiveDocumentDialog`) nunca apaga, e um arquivado só pode ser baixado. As recusas são lidas por `useDocumentFailure` (`FILE_TOO_LARGE`, `FILE_TYPE_NOT_ALLOWED`, `STORAGE_DISABLED`, `VERSION_CONFLICT`, `DOCUMENT_ARCHIVED`...). Histórico (`PersonHistory`): só leitura, paginado, com quando, o evento (rótulo por código em `historyEvents.ts`; um código desconhecido aparece como veio), a entidade (aluno, responsável ou vínculo, com o número), quem fez (um Admin aparece como "Administração" para a Secretaria; sem autor, "Sistema") e só os nomes do que mudou, nunca valores (`readHistoryChanges`: os `fields=` de um cadastro, ou as partes de um vínculo que diferem entre antes e depois). Não é a trilha de segurança, que fica na Auditoria. As duas abas guardam a resposta com a pessoa que a pediu, então trocar de pessoa nunca mostra os dados de outra, e o histórico é relido quando o perfil é. **LGPD** (JLM-253, só Admin, como no backend; `shared/people/privacy/`): o menu de ações dos dois perfis ganha, pelo `usePersonPrivacy`, "Exportar dados (LGPD)" (`downloadPersonExport`: tudo o que o backend guarda da pessoa, baixado na hora como `dados-pessoais-<id>.json`, nunca pelo nome; a exportação é auditada) e, para quem está inativo, "Anonimizar (LGPD)" (`AnonymizeDialog`: o protocolo do pedido do titular, de 3 a 60 caracteres, e a confirmação explícita de que não tem volta; recusas `MUST_BE_INACTIVE`, `REQUEST_REF_REQUIRED`, `ADMIN_CANNOT_BE_ANONYMIZED`). A lista de Alunos ganha "Limpar rascunhos" (`DraftCleanupDialog`), que roda agora a retenção de rascunhos abandonados que o backend também roda toda noite; o prazo é política do backend: quando nada é apagado, a tela diz o motivo com o `retentionDays` da resposta (backend `1c3385c`). **Descartar um rascunho** de que nada depende (sem vínculo, convite aberto ou confirmado, nem documento) o apaga de vez: a resposta vem com `status: "DELETED"` (`StudentStateResult`) e o perfil volta para a lista de Alunos; senão ele fica inativo (backend `5e2670d`, RB-88). Uma pessoa anonimizada (o nome vira "Pessoa anonimizada") vem com `anonymized` no detalhe, no 360, nas linhas das listas e no responsável dentro do 360 do aluno: o perfil ganha a tag "Anonimizado" e o aviso `AnonymizedNotice` e oferece só a exportação (nem editar, nem mudar a situação, nem vínculos, convites ou documentos, que ficam só para baixar), o formulário de edição mostra que ela não pode ser alterada em vez de abrir, e as listas mostram a tag ao lado da situação (`AnonymizedBadge`, de `shared/people/privacy/`). Uma alteração que ainda chegue ao backend responde 409 `PERSON_ANONYMIZED`, que toda jornada de pessoas mostra com a mesma mensagem. **Falhas inesperadas** das telas de pessoas passam pelo `useFailureMessage` (`shared/people/`): `PERSON_ANONYMIZED` vira a sua mensagem, e o resto ganha a referência do suporte, o `correlationId` da chamada (`getErrorCorrelationId`). Documento e e-mail chegam mascarados do backend e aparecem assim; o código do aluno (`ALU-000001`) é cadastral, não número de matrícula. Salvar aluno ou responsável nunca cria acesso: o acesso do aluno é a senha temporária (ele entra pelo apelido), e o do responsável, o convite. O backend não tem idempotência aqui (PE-15): um cadastro sem resposta é relido antes de tentar de novo. Turma, matrícula e cobrança nunca vêm de Pessoas. Cobertos pelo E2E (`e2e/people.spec.ts`, `e2e/students.spec.ts`, `e2e/guardians.spec.ts` e `e2e/student-links.spec.ts`, `e2e/person-documents.spec.ts` e `e2e/people-privacy.spec.ts`, com o backend simulado em `e2e/support/people.ts`, que guarda os vínculos, os convites e os documentos).

### Estrutura acadêmica (P04)

O contrato é o `docs/P04_CONTRATO.md` do backend (conferido no `61c4178`), com as decisões da seção 6b do `sfback-basis.md`; as rotas ficam em `/api/academic` e o OpenAPI é a fonte final dos nomes. **Quem abre o quê (CT09):** Admin, Secretaria e Coordenação gerem a estrutura nas unidades das suas atribuições (a Coordenação nunca abre Usuários, Convites nem Pessoas), o Professor só lê (e só as turmas onde tem vínculo vigente), o Aluno e o Responsável só veem o calendário publicado e o Financeiro não vê nada; `pageRoles` segue isso, e o backend confere de novo em toda chamada (`eligibleActions` de cada item é a decisão do servidor). O grupo Acadêmico do menu tem Visão geral (`academicOverview`), Períodos letivos (`periods`), Etapas e séries (`gradeLevels`), Disciplinas (`subjects`), Ofertas (`offers`), Salas (`rooms`), Turmas (`classes`) e Calendário (`academicCalendar`), além do Diário de classe e dos Boletins, de outros épicos. Há um service por controller do Swagger: `academicPeriods`, `academicCatalog` (etapas, séries, disciplinas, pesquisa antes de criar, ofertas, salas e turnos), `academicClasses` (turmas e vínculos docentes), `academicClassDetail` (abas da turma, capacidade, histórico e a visão geral) e `academicCalendar`. **A ocupação, as vagas e os alunos da turma vêm da Matrícula (EPIC 6)**, que conta as matrículas ativas (desde o backend `ecc5475`). Quando ela não responde, eles vêm `UNAVAILABLE`, que nunca é mostrado como zero. Inativar uma turma com matrícula ativa é recusado (409 `ACADEMIC_DEPENDENCY_ACTIVE`), e sem a fonte também (503 `ACADEMIC_SOURCE_UNAVAILABLE`), porque o silêncio não prova que não há alunos. Os bloqueios e impedimentos dos impactos (`blockers`, `activationImpediments`...) vêm do backend como frases em inglês, não como códigos. A P04 não tem `Idempotency-Key`: uma criação repetida é contida pela unicidade no banco. **Os bloqueios em inglês nunca aparecem como vieram**: `readAcademicBlocker` (`src/pages/shared/academic/academicBlockers.ts`) reconhece cada frase do backend e a traduz pela chave `academic.blockers.*` (com a contagem e, numa unidade, o nome dela), uma frase desconhecida vira um texto genérico, e `readDependencyMessage` separa as que um 409 `ACADEMIC_DEPENDENCY_ACTIVE` lista na mensagem (lida com `getErrorMessage`, de `@/services/httpClient`, só para isso: nunca se decide pelo texto). As telas dividem o que fica em `src/pages/shared/academic/`: `useAcademicUnits` (as unidades conhecidas e as que a pessoa gere: só Admin e Secretaria listam `/api/school-units`, e os outros papéis conhecem as unidades pelas próprias atribuições) e `useAcademicLabels` (situações, tipos, intervalos de datas e bloqueios). As listas usam o `usePeopleList`/`PeopleListError` de `shared/people`. **Períodos letivos** (`Periods`, P04-S02): lista com busca, ano e situação; "Novo período" e "Editar" num modal com revisão antes de salvar (`PeriodFormModal`: nome, ano, tipo, datas e unidades; um período nasce configurado; datas invertidas ou sobrepostas marcam os dois campos; um conflito de versão relê e mantém o rascunho com o `ConflictNotice` da Minha Organização); "Ativar" (`ActivatePeriodDialog`) e "Encerrar" (`ClosePeriodDialog`: lê o impacto, lista o que impede e pede o motivo; nada é apagado). Cada linha oferece só o que `eligibleActions` permite, e o Professor só lê. **Etapas e séries** (`GradeLevels`, P04-S03, duas abas emendadas: `StagesTab` e `GradesTab`) e **Disciplinas** (`Subjects`, P04-S04): o catálogo é da instituição; cada cadastro abre num modal (`StageFormModal`, `GradeFormModal`, `SubjectFormModal`) que, ao criar, mostra os itens parecidos enquanto se digita (`CatalogSimilar`, a pesquisa antes de criar do backend; só um aviso), aponta nome ou código repetido no próprio campo e, num conflito de versão, mantém o rascunho com o `ConflictNotice`, tudo pelo `useCatalogSave`; a série nasce numa etapa ativa e nunca muda de etapa. Inativar e reativar passam pelo `CatalogStatusDialog` (que lê o impacto, quando há, e bloqueia a confirmação listando o que depende do item; nada é apagado), e as listas curtas para seletores vêm do `useAcademicDirectory`. **Uma página do backend tem no máximo 100 itens** (`PageParams`; mais que isso responde 400): uma lista lida inteira para um seletor pede `academicMaxPageSize` (`shared/academic/academicLimits.ts`), nunca mais, e o backend simulado do E2E recusa um `size` acima de 100 como o real (um pedido de 200 deixava a aba Séries sem etapas, o formulário de turma sem ofertas e o calendário sem itens). **Ofertas** (`Offers`, P04-S03) e **Salas** (`Rooms`, P04-S04): uma oferta é uma série do catálogo oferecida numa unidade e num período, com as disciplinas que ensina, e é sobre ela que a turma nasce. "Nova oferta" (`OfferFormModal`) escolhe a unidade entre as que a pessoa gere, o período entre os não encerrados que incluem a unidade e a série ativa; unidade, período e série nunca mudam depois, a combinação repetida aponta o campo da série, e a oferta criada segue direto para as disciplinas (`OfferSubjectsModal`: as ativas do catálogo, mais as já ligadas que foram inativadas, para tirar; a lista inteira substitui a atual, e um conflito de versão relê a oferta e mantém a escolha). As salas são lidas uma unidade por vez (a primeira conhecida, de início), com busca e situação filtradas na tela; o nome é único na unidade, a sala nunca muda de unidade e só é renomeada (`RoomFormModal`; o backend não lê uma sala sozinha, então um conflito relê a lista), e numa unidade que a pessoa só consulta a tela avisa e não oferece "Nova sala". As duas inativam e reativam pelo `CatalogStatusDialog`, sem impacto prévio: o backend recusa listando as turmas que dependem (`ACADEMIC_DEPENDENCY_ACTIVE`). **Turmas** (`Classes`, P04-S05) e **detalhe da turma** (`ClassProfile`, `/academic/classes/:classId`, `paths.classProfile`, P04-S06): a lista busca por código ou nome e filtra por unidade, período e situação, e mostra se a turma está pronta para matrícula (`eligibleForEnrollment`, calculado pelo backend, nunca editável) e o que ainda falta sem impedir (`pendencies`, hoje "Sem professor"). "Nova turma" (`ClassFormModal`) nasce em preparação dentro de uma oferta ativa: a unidade entre as que a pessoa gere, o período não encerrado que a inclui, a série entre as ofertas ativas da unidade no período (relidas a cada par), as disciplinas da oferta (todas marcadas de início), código único na unidade e período (repetido aponta o campo), capacidade inteira, turno da lista fixa e uma sala ativa da unidade **ou** "Sem sala física", nunca as duas nem nenhuma; a turma criada abre o detalhe. Ativar e inativar passam pelo `ClassStateDialog`, que lê o impacto antes (`activationImpediments` ou `inactivationBlockers`, traduzidos) e bloqueia a confirmação enquanto houver algo; inativar tem motivo opcional e, enquanto a Matrícula não responde, fica bloqueado (503 `ACADEMIC_SOURCE_UNAVAILABLE`). O detalhe mostra as abas que o backend libera em `tabs` e que já existem na tela (Geral, `ClassGeneral`; Alunos, `students/`; Professores, `teachers/`; Capacidade, `capacity/`; Histórico, `history/`; cada uma lida na própria chamada, e o Professor da turma só tem as três primeiras), e uma turma fora do alcance (para o Professor, uma em que não leciona hoje) responde como não encontrada. **Aba Professores** (`ClassTeachers`, P04-S07): os vínculos da turma com a disciplina, as datas (inclusivas; sem fim = aberto), a situação calculada para hoje (Agendado, Vigente, Encerrado) e a docência compartilhada; o Professor vê só os dele. O mesmo professor na mesma disciplina e datas é recusado na hora (`ACADEMIC_DUPLICATE_CODE`), e outro professor só entra com a docência compartilhada marcada nos dois vínculos (`ACADEMIC_JOINT_REQUIRED`, no campo). Uma data no passado é só do Admin e da Coordenação da unidade (`useCanBackdate`, de `teachers/teacherLinkForm.ts`), que dão o motivo; para a Secretaria a tela já recusa no campo. Editar muda só as datas e a docência compartilhada (trocar professor ou disciplina é encerrar e criar outro), e encerrar (`EndTeacherLinkDialog`) pede o último dia (hoje, de início) e o motivo; nada é apagado, e o vínculo encerrado continua na lista, sem ações. O Histórico (`ClassHistory`, só a gestão) filtra por tipo e período (intervalo invertido avisado na tela), rotula o evento pelo código (`history/classEvents.ts`; desconhecido aparece como veio), mostra os nomes dos campos alterados, o antes e depois que o backend guarda (situação, limite, datas do vínculo) e o motivo; sem autor, "Sistema". Não é a auditoria de segurança. A inativação de unidade (Minha Organização) também mostra o impacto acadêmico: turmas em preparação ou ativas, vínculos de professor em andamento e períodos abertos (`liveClasses`, `openTeacherLinks`, `openPeriods` do `deactivation-check`). ### Matrícula (P05, EPIC 6)

O contrato é o `docs/P05_CONTRATO.md` do backend (conferido no `1f7b763`), com as decisões da seção 6c do `sfback-basis.md`. Ele é entregue em fatias, e a tela acompanha só o que já existe:

- **Ainda não existem:** documentos, condições financeiras, contrato, aceite, exceções e a confirmação, que esperam a Fatia 3 em diante, o EPIC 8 e decisões de Produto.

**Quem abre:**

- O Admin opera na instituição inteira e a Secretaria nas unidades dela (`useEnrollmentAccess`, de `src/pages/shared/enrollments/`).
- O Financeiro e a Coordenação só leem, nas unidades deles.
- Professor, Aluno e Responsável não abrem (`pageRoles` de `enrollments`/`enrollmentProfile`).
- As ações de cada matrícula são só as que o backend libera em `eligibleActions`.
- Uma matrícula fora do alcance responde 404 `ENROLLMENT_NOT_FOUND`, igual a inexistente.

**Matrículas** (`/administration/enrollments`, página `Enrollments`, no grupo Administração do menu):

- Lista pelo `usePeopleList`, da alteração mais recente para a mais antiga, com busca por nome ou código do aluno e filtros por unidade e situação. As abandonadas só aparecem pedidas.
- Uma preparação mostra quantas pendências tem.
- "Nova matrícula" (`NewEnrollmentModal`) escolhe uma unidade ativa onde a pessoa opera e um aluno já cadastrado nela (`searchEnrollmentStudents`, que divide o limite de buscas de Pessoas). Ninguém é cadastrado ali. Um aluno não ativo pode ser preparado, mas a tela avisa que só um ativo é confirmado.
- Um aluno que já tem matrícula viva na unidade (409 `ENROLLMENT_CONFLICT`) não ganha outra. A tela acha a existente pela lista (nunca pelo texto da mensagem) e oferece abri-la.

**A matrícula** (`/administration/enrollments/:enrollmentId`, `paths.enrollmentProfile`, página `EnrollmentProfile`) tem as abas emendadas Preparação, Responsáveis, Turma e Histórico:

- A **Preparação** (`EnrollmentPreparation`) mostra:
  - o aluno como Pessoas o tem agora, com o link para o cadastro só para quem abre Pessoas (é lá que ele é corrigido);
  - os responsáveis e a turma escolhidos;
  - o que falta, pelo código da pendência (`useEnrollmentLabels`; a `message` do backend é em inglês e nunca aparece);
  - as etapas ainda não avaliadas (`notEvaluated`), que nunca contam como cumpridas.
- "Abandonar preparação" (`AbandonEnrollmentDialog`) pede o motivo, de 1 a 500 caracteres, e o `version`.
- A aba **Responsáveis** (`EnrollmentGuardians`) lista todos os responsáveis vinculados ao aluno em Pessoas, com vínculo vigente ou encerrado, o parentesco e as três responsabilidades do vínculo lá.
  - O parentesco vem do catálogo, que só Admin e Secretaria leem; para os outros a tela não o pede (`useRelationshipTypes(enabled)`).
  - Quem participa, quem é financeiro e quem assina são escolhas explícitas desta matrícula, nunca deduzidas do parentesco. São editadas no lugar ("Alterar escolhas") e salvas como o conjunto inteiro, com o `version`.
  - Um vínculo encerrado não pode ser escolhido, e um escolhido antes de encerrar aparece assim.
  - O vínculo é criado ou corrigido no cadastro do aluno, nunca aqui.
  - Num conflito de versão a página relê a matrícula, mantendo na tela a resposta anterior enquanto relê, para o rascunho não se perder.
- A aba **Turma** (`EnrollmentClass`):
  - Mostra a turma escolhida, com turno, limite, ocupação lida agora (e quando) e vagas. Uma ocupação que não pôde ser lida aparece como "indisponível", nunca zero.
  - Lista as turmas da unidade abertas para matrícula (`listEnrollmentClasses`), lidas só quando a pessoa vai escolher.
  - Escolher a primeira turma salva na hora. Trocar ou desfazer a escolha (`classId: null`) pede confirmação, porque as etapas que dependem dela serão revistas.
  - Escolher nunca reserva vaga, e a tela diz isso.
  - O servidor confere a turma de novo a cada mudança (`ENROLLMENT_CONTEXT_INVALID`).
- O **Histórico** (`EnrollmentHistory`) mostra o evento, o autor (sem autor, "Sistema") e os nomes do que mudou. Numa mudança de situação, mostra o antes e o depois. Não é a auditoria.
- Salvar uma preparação nunca cria acesso, cobrança nem matrícula ativa.

Coberto pelo E2E `e2e/enrollments.spec.ts`, com o backend simulado em `e2e/support/enrollments.ts`.

### `src/pages/` guarda as views roteadas, e fica propositalmente fora de `src/ds-components/`

`src/pages/<PageName>/` segue o mesmo formato de pasta por componente que `src/ds-components/` (`PageName.tsx` + `PageName.styles.ts` + `index.ts`, com o `index.ts` de cada pasta de camada reexportando todas as páginas — ver `src/pages/index.ts`), mas páginas **não** fazem parte das camadas de componentes do Atomic Design abaixo e não recebem `.stories.tsx`/`.test.tsx`: são composições roteadas de atoms/molecules/organisms, não peças reutilizáveis do design system documentadas no Storybook ou testadas unitariamente de forma isolada.

**Toda página atrás do login abre com o `PageHeader`** (`src/ds-components/molecules/PageHeader/`): o título (o `<h1>` da página, o mesmo texto do item do menu), uma descrição e um ícone, os dois opcionais. Enquanto a descrição de uma página não é definida, ela usa `common.placeholderDescription` (um lorem ipsum); quando for, ganha a própria chave na seção da página (como `myOrganization.subtitle`). Quando a página tem seções, as abas (`Tabs`) vêm logo abaixo do `PageHeader`, **sempre com `attached`**: o conteúdo de cada aba (um cartão) fica emendado na aba selecionada, sem espaço entre os dois, venha ele de fora do `Tabs` ou do `content` de cada item, que com `attached` também começa colado na barra. Numa tela estreita (abaixo de `md`) as abas ficam um passo menores e a barra rola de lado: uma borda com abas escondidas se apaga num degradê (`data-overflow-start`/`data-overflow-end`), a rolagem para em abas inteiras e a aba selecionada rola para dentro da vista, sem mover a página. Não quebre as abas em várias linhas nem as troque por outro controle sem pedido (ver os perfis de aluno e responsável, e a Minha Organização, que mantém o conteúdo de todas as abas montado e só esconde o das outras, para uma edição em andamento não se perder ao trocar de aba). O breadcrumb do topo é do `AppShell`, não da página: o primeiro item leva o ícone do item do menu a que a página pertence.

**A página inicial (`Home`, `/home`) apresenta o SchoolFlow360º e as principais áreas**: um cartão com a saudação pelo primeiro nome, um texto curto sobre o produto e três ideias (`homePillars`), e um cartão por funcionalidade principal (`homeFeatures`, em `Home/Home.features.ts`: a página de destino, o ícone e a chave dos textos em `home.features`), cada um com um botão "Abrir" para a página. Só aparecem as áreas que a pessoa pode abrir (`canOpenPage` com o `pageRoles` da página, a mesma regra do menu). Uma área nova é uma entrada em `homeFeatures` e os textos nos cinco idiomas.

**Uma página grande se divide em subpastas da própria pasta da página**, uma por aba ou área, mais `shared/` para o que elas usam em comum — ver `src/pages/MyOrganization/` (`overview/`, `branding/`, `units/`, `shared/`, além de `MyOrganization.constants.ts` e de um só `MyOrganization.styles.ts`). **Cada aba é um único cartão principal** (`TabCard`, elevado e emendado na aba) com as seções dentro como **sub-cartões** (`SectionCard`: borda fina, sem sombra própria), e **todo botão dentro de um sub-cartão usa `size="small"`** (um nível abaixo do padrão: "Editar", Cancelar/Salvar, "Ver todas"...), enquanto os do cartão principal e dos modais continuam no padrão; uma aba de bloco único, como a lista de unidades, põe o conteúdo direto no `TabCard`, com o título dele. Continuam sendo página: sem stories nem testes unitários, cobertas pelo E2E (`e2e/my-organization.spec.ts`). **A Secretaria só consulta a Minha Organização** (matriz ORG-M01 a M04): o `MyOrganizationAccessContext` (`MyOrganization/shared/myOrganizationAccess.ts`, lido com `useCanManageMyOrganization`) tira todo controle de edição (os "Editar", "Nova unidade", as ações da unidade e o formulário da identidade, trocado pelo `PublishedBrandingView`), e a página lê o resumo da organização (`getOrganizationOverview`, sem endereço nem observação interna, que então não aparecem), a identidade publicada (`getPublishedOrganizationBranding`; nada publicado é a aparência padrão) e só as unidades dela. **Informação só de leitura se mostra com a `DescriptionList`** (pares rótulo/valor em grade; valor vazio vira "Não informado", via `common.notInformed`), e **uma seção editável segue o padrão "ler primeiro, editar no lugar"**: o `EditableSectionCard` + `useSectionForm` de `MyOrganization/shared/` trocam a leitura pelo formulário (`react-hook-form`, como o Login) com Cancelar/Salvar, Salvar desligado enquanto nada mudou, o aviso de alterações não salvas ligado, e o salvar devolvendo um `SaveResult` (`saved`/`failed`/`conflict`, de `MyOrganization/shared/saveResult.ts`; só no `saved` a seção volta à leitura). **Um conflito de versão (409) nunca perde o que o usuário digitou**: a página relê o registro e o formulário (seção, modal de unidade ou identidade visual) continua aberto com o rascunho e o `ConflictNotice` (`MyOrganization/shared/`), que mostra a versão atual sob demanda e oferece descartar; salvar de novo grava por cima, já com o `version` relido. Na inativação de unidade, o conflito relê o impacto e pede a confirmação de novo. A troca entre leitura e formulário é animada: a altura do cartão desliza até a do conteúdo novo (`useAnimatedHeight`, que mede o conteúdo com um `ResizeObserver` e só corta o que transborda durante a animação, para o menu de um `Select` abrir inteiro com o cartão parado; ignora a altura zero de uma aba escondida e respeita o "reduzir movimento"), e o conteúdo novo entra com um fade leve, sem animar na primeira renderização. Formulário médio de um item de lista (ex.: uma unidade) vai num `Modal`, renderizado só enquanto aberto para cada abertura partir dos dados atuais.

**As props JSX de um componente, dentro de uma página, seguem uma ordem específica** — não a ordem puramente alfabética que o `perfectionist` impõe para os object literals de `src/ds-components/`/`src/components/` (ver a seção de convenções de ESLint/Prettier abaixo), já que atributos JSX não são cobertos por essa regra de forma alguma. Ordene assim: primeiro as props não booleanas e que não sejam `style`, em ordem alfabética; depois as props booleanas abreviadas (shorthand), também em ordem alfabética entre si; e por fim `style`, sempre por último. Dentro do próprio objeto `style`, as chaves ficam em ordem alfabética independente do tipo de propriedade CSS que representam. Não é imposto por lint — revise manualmente. Exemplo, o primeiro `Card` em `Login.tsx`:

```tsx
<Card
  borderRadius="5xl"
  translucent="high"
  elevated
  style={{
    display: "flex",
    flexDirection: "column",
    gap: spacing[20],
    padding: spacing[40],
  }}
>
```

`borderRadius`/`translucent` (alfabéticas, não booleanas, não `style`) vêm primeiro, `elevated` (a única booleana) vem em seguida, e `style` vem por último com suas próprias chaves (`display`/`flexDirection`/`gap`/`padding`) em ordem alfabética.

Uma exceção: as props de breakpoint do `Grid.Col` (`xs`/`sm`/`md`/`lg`/`xl`/`xxl`) são ordenadas do menor para o maior, não alfabeticamente — ex.: `<Grid.Col xs={12} md={6}>`, não `<Grid.Col md={6} xs={12}>`.

### `src/utils/` guarda funções puras e transversais

`src/utils/<moduleName>/` é para funções simples, agnósticas de framework, reutilizadas em múltiplos componentes/páginas — não vinculadas à pasta de um único componente. Cada módulo tem sua própria pasta espelhando o formato de pasta de componente (`<moduleName>.ts` + `index.ts` reexportando-o, ex.: `export * from "./formats"`) e um `<moduleName>.test.ts` co-localizado (ver `src/utils/formats/`). O `src/utils/index.ts` no topo reexporta cada pasta de módulo por sua vez, para que consumidores importem diretamente de `@/utils`. Os módulos usam apenas named exports, nunca export default. `formats/formats.ts` é a fonte única de verdade para formatação de exibição (`formatCpf`, `formatCnpj`, `formatCep`, `formatPhone`, `formatCreditCard`, `formatCurrency`, `formatExpiry`) — cada uma recebe uma `string` bruta/possivelmente "suja" e retorna a string formatada para exibição, fazendo internamente sua própria extração de dígitos e, quando o formato tem tamanho fixo, o truncamento. A prop `mask` do `Input` (`src/ds-components/molecules/Input/Input.masks.ts`) é um despachante fino sobre essas mesmas funções em vez de ter implementação própria — não duplique a lógica de um formatador dentro de um componente quando o valor puder, em vez disso, ser formatado para exibição via `@/utils/formats` a partir de qualquer lugar da aplicação. `loadingStore/loadingStore.ts` é outro módulo desse tipo — ver a seção `src/services/httpClient/` abaixo para entender sua finalidade. `session/session.ts` guarda a sessão do usuário logado (`saveSession`/`getSession`/`getSessionToken`/`hasSession`/`clearSession`) criptografada no `localStorage` via `storage/` (que usa o `crypto.subtle`, só disponível em contexto seguro: `https` ou `localhost`). Aberto o servidor de dev pelo IP da rede em `http`, nada pode ser guardado: o login avisa (`isSecureStorageAvailable`) e não chama o backend, para não abrir uma sessão que a página não guardaria (para testar pela rede, `bun run dev:https`); o access token é o `token` da resposta do login (o `accessToken` é o que o endpoint de refresh devolve e não é guardado), e com ele o `context` de quem entrou (nome, papéis, atribuições), que vem do login e é atualizado com `updateSessionContext`. Uma sessão com `expiresAt` vencido fica `stale` (o token de acesso dura 1 h, o de renovação 7 dias): não é inexistente, e só uma renovação recusada pelo backend a encerra. `access/access.ts` traz `hasAnyRole` (um Admin passa onde passa a Secretaria, como no backend), `canOpenPage`, `getDisplayRoles` (os papéis para mostrar, o mais amplo primeiro) e `getGrantableRoles` (os papéis que quem entrou pode conceder). O login não tem mais bloqueio próprio: depois de senhas erradas repetidas o backend responde 429 (1 minuto na 3ª, 3 minutos a cada 5ª, por e-mail) com o `Retry-After`, e a página mostra a espera como contagem regressiva no botão (1 minuto quando o cabeçalho não vem ou não pode ser lido; o CORS do backend o expõe). `formats/formats.ts` também traz `formatCountdown` (`1:00`, `0:05`), usado no botão travado do login, e `formatFileSize` (`340 KB`, `1,5 MB`, no formato de número do idioma). `phone/phone.ts` cuida de **telefone de qualquer país** sobre a `libphonenumber-js` (metadados `max`, os que conferem se o número existe no plano do país; os menores só olham o tamanho): `formatPhoneInput` formata enquanto se digita (e, quando só um caractere de formatação foi apagado, apaga o dígito antes dele, senão o formatador o devolvia), `isValidPhone` valida, `formatPhoneForDisplay` mostra no formato nacional um número do país padrão e no internacional os demais, e `toInternationalPhone` dá o formato salvo (sempre internacional, `+55 85 3333 1100`). Um número sem `+` é lido como do país passado (padrão `BR`). `splitPhone` separa um número internacional em país e parte nacional (no formato do país), `joinPhone` junta os dois de volta no formato internacional, e `getPhoneCallingCode` dá o código do país (`55`): são a base do `PhoneInput`. `countries/countries.ts` guarda os países como código ISO 3166-1 alfa-2 (`BR`, `PT`), com os nomes vindos do navegador (`Intl.DisplayNames`, no idioma pedido): `getCountryOptions` para um campo de país, `getCountryName`, `isCountry`, `defaultCountry` (`BR`) e `toCountry`, que lê o país que o backend guarda como texto livre (um código, ou um nome em qualquer idioma do app, sem diferenciar maiúsculas e acentos). **A Minha Organização segue o país da organização** (`OrganizationCountryContext`, em `MyOrganization/shared/`): ele define como um telefone sem `+` é lido e mostrado (`usePhoneFormatter`) e o formato do endereço das unidades, que não têm país próprio; o endereço da organização tem o campo País (`AddressFields withCountry`). Um endereço brasileiro tem CEP com máscara e busca no ViaCEP e a UF numa lista obrigatória; o de outro país, código postal e estado/região em texto livre (a região opcional), e trocar o país limpa os dois. O país é salvo como código. **Todo campo de telefone é o `PhoneInput`** (`src/ds-components/molecules/PhoneInput/`, ver "Campos de formulário"), nunca um `Input` com `type="tel"` nem a `mask="phone"`, que é só brasileira e continua existindo para o design system. `email/email.ts` traz `isValidEmail`, que espelha o `@Email` do backend (Hibernate Validator: sem ponto no início, no fim ou dobrado na parte local, até 64 caracteres nela, rótulos de domínio sem hífen nas pontas) e exige um ponto no domínio, um pouco mais rígido que o backend; use-o em vez de uma regex própria nos formulários que o backend valida. `address/address.ts` traz `formatAddress` (o endereço numa linha, pulando o que falta), `formatCityState`, `emptyAddress` e `brazilianStates` (as 27 UFs). `userAgent/userAgent.ts` traz `summarizeUserAgent`, que reduz o user agent de uma sessão ao navegador e ao sistema ("Chrome", "Windows"), para a pessoa reconhecer onde a abriu. `strings/strings.ts` traz `getInitials` (iniciais de um nome, usado pelo atom `Avatar`), `getShortName` (só o primeiro e o último nome, que o `UserIdentity` mostra por padrão para um nome longo não alargar o elemento) `normalizeForSearch` (sem acento e em minúsculas, para uma busca casar "São José" com "sao jose") e `joinIds`, que junta ids para um atributo IDREF (`aria-describedby`, ...) ignorando os ausentes e devolvendo `undefined` quando não sobra nada, para o atributo nem ser renderizado.

- **Nunca use `.replace(/\D/g, "")` inline para remover caracteres não numéricos.** Use `stripNonDigits`, exportado de `@/utils/formats` (ver seu uso no tratamento `numeric` de `Input.tsx` e em `viaCep.ts`). Manter isso em um único lugar significa que uma mudança futura no que conta como "um dígito" (ou a troca da implementação) só precisa acontecer uma vez.

### `src/hooks/` guarda hooks compartilhados e transversais

`src/hooks/<hookName>/` segue o mesmo formato de pasta por módulo de `src/utils/` (`<hookName>.ts` + `index.ts` + `<hookName>.test.ts` co-localizado), reexportado pelo `src/hooks/index.ts`, e é importado via `@/hooks`. É o lugar de hooks que não pertencem a um componente só (`useTooltip`, por exemplo, continua co-localizado com o `Tooltip` por ser fortemente acoplado a ele). Hoje há `useMediaQuery(query)`, que assina uma media query via `useSyncExternalStore` e devolve se ela casa — onde `matchMedia` não existe, devolve `false` (o happy-dom dos testes unitários tem um, que responde por uma janela de 1024x768, então um teste que depende dele o stuba). O `Sidebar` o usa com `not all and ${media.md}` (a própria token de breakpoint, negada) para saber se a tela é compacta; em testes, `vi.stubGlobal("matchMedia", ...)` simula uma tela compacta e `vi.unstubAllGlobals()` no `afterEach` limpa. `useDebouncedValue(value, delayMs)` devolve o valor só depois que ele para de mudar (uma busca que consulta o backend a cada pausa, não a cada tecla), e `useSignedInUser()` devolve quem entrou (o dado do loader do `AppShell`), `null` fora das páginas atrás do login. Há também `useSessionExpiry(onExpire)`, que chama `onExpire` quando o token de acesso guardado chega ao `expiresAt`, mesmo com a página parada; `onExpire` renova ou encerra a sessão e devolve se ela continua, e então o hook passa a vigiar o novo vencimento (ou tenta de novo depois de uma pausa, se o backend não respondeu). Usado pelo `AppShell`; teste mockando `getSessionState` com `vi.useFakeTimers()`, e `useCountdown()`, uma contagem regressiva em segundos (`{ isRunning, secondsLeft, start(seconds) }`) que acompanha o horário de término em vez de decrementar um contador, então um tick atrasado (aba em segundo plano) não a estica — usada para travar o "reenviar" da recuperação de senha por 60s; teste com `vi.useFakeTimers()`.

### `src/i18n/` guarda o suporte a múltiplos idiomas

`src/i18n/` é construído sobre `react-i18next`/`i18next` (mais `i18next-browser-languagedetector`, que detecta o idioma do navegador):

- `i18n.ts` (reexportado via `index.ts`, importado como `@/i18n`) monta a instância do `i18next` com os plugins `LanguageDetector`/`initReactI18next`, os catálogos de `locales/` como `resources`, `fallbackLng: "pt-BR"` e `supportedLngs` (hoje `["pt-BR", "pt-PT", "en", "es", "fr"]`, exportado como `supportedLanguages`). `en`/`es`/`fr` valem para todas as regiões do idioma (`en-GB`, `es-MX`, `fr-CA`...); o português é separado por região, e o `pt-BR` vem primeiro de propósito: um navegador só em `pt`, ou de outro país lusófono (`pt-AO`...), recebe o primeiro `pt-*` da lista, então só `pt-PT` recebe o português europeu. Um idioma novo é um `locales/<código>.ts` tipado como `TranslationResource` mais a entrada em `supportedLanguages`/`resources`. É importado uma única vez em `main.tsx`, que envolve a árvore inteira em `<I18nextProvider i18n={i18n}>` (por fora de `GlobalStyle`/`RouterProvider`). **O `StrictMode` fica desligado no servidor de desenvolvimento** (`import.meta.env.DEV`): a execução dupla de effects fazia toda chamada sair duas vezes localmente; no build de produção ele envolve a árvore, onde não tem efeito.
- `locales/ptBR.ts` é a fonte única de verdade: `export const ptBR = { <página ou área>: { chaveCamelCase: "texto em pt-BR", ... }, ... }` e `export type TranslationResource = typeof ptBR`, derivado do próprio objeto em vez de escrito à mão. Cada página ganha sua própria chave de topo (ex.: `login`), igual a um namespace.
- `locales/en.ts` (e `es.ts`, `fr.ts`, `ptPT.ts`, e qualquer locale futuro) é tipado explicitamente como `TranslationResource` (`export const en: TranslationResource = {...}`) em vez de ter seu tipo inferido — isso faz o `tsc` barrar uma chave esquecida ou digitada errado em vez de deixar passar silenciosamente uma string sem tradução.
- O augmentation `declare module "i18next"` em `i18n.ts` (o mesmo padrão do `declare module "axios"` em `httpClient.ts`) registra `TranslationResource` como o shape de `CustomTypeOptions["resources"]["translation"]`, então `t("login.emailLabel")` ganha autocomplete e uma chave inexistente também quebra o `tsc`, não só em runtime.
- Um componente consome isso com `const { t } = useTranslation()` (do pacote `react-i18next`) — na ordenação do corpo do componente (ver a seção abaixo), esse hook entra no bloco de "hooks customizados", antes de qualquer `useState`. Ver `src/pages/Login/Login.tsx` como referência: toda string de interface vira `t("login.algumaChave")`, exceto nomes próprios/marca (`SchoolFlow360º` continua literal, do mesmo jeito que o `name` de um `Icon` não é traduzido nas stories do Storybook — ver a seção de Storybook abaixo).
- Isso cobre `src/pages/` (o texto que o usuário final vê) e o que é a casca do próprio app, não peça reutilizável: o template `AppShell` (menu, breadcrumb e topbar, chave `shell`) e o `GlobalLoading`, montado fora de qualquer página. **Não** se aplica aos demais componentes de `src/ds-components/`/`src/components/` nem às suas stories — eles continuam sem texto fixo próprio (recebem conteúdo via props) ou, quando uma story precisa de conteúdo de exemplo, esse conteúdo permanece pt-BR conforme a regra já documentada na seção de Storybook, já que o Storybook documenta o design system, não a experiência final do produto.
- Quando um componente precisa de um texto de interface próprio (um `aria-label` de botão só com ícone, uma mensagem de estado), ele vira uma **prop opcional com padrão em pt-BR**, e quem renderiza em uma página passa `t(...)` — ver `emptyMessage`/`loadingMessage`/`pageLabel`/... da `Table`, `collapseLabel`/`expandLabel`/`navLabel` do `Sidebar`, `showPasswordLabel`/`hidePasswordLabel` do `Input` (o botão de mostrar/ocultar senha que todo `type="password"` ganha; as páginas passam `common.showPassword`/`common.hidePassword`), `clearLabel` do `DateInput`, `openLabel` do `ColorPicker`, `placeholder` do `FileUpload` e `label` do `Loading`. Não fixe um texto novo direto no JSX de um componente.
- Rótulos de opções que vêm de dados (ex.: o modelo de operação e a situação no Minha Organização) não ficam junto dos dados: a fonte guarda só os códigos (o tipo `OperationModel`, de `@/models`) e a página monta o rótulo com uma chave por código (``t(`myOrganization.operationModels.${value}`)``), que o tipo literal do código mantém checada pelo `tsc`.
- Login, Minha Organização e AppShell já estão migrados. **Não há seletor de idioma, por decisão de produto**: o idioma é sempre o do navegador (`navigator.languages`, a configuração de idioma do sistema/navegador de quem abre o site — não a localização geográfica), detectado a cada visita. O detector usa `order: ["navigator"]` e `caches: []`, então nada é lembrado entre visitas nem lido de query string/cookie/storage; um idioma não suportado cai no `fallbackLng` (`pt-BR`). Não reintroduza um seletor nem um cache de idioma sem pedido explícito. `i18n.ts` também mantém `<html lang>` igual ao idioma ativo (o `index.html` parte de `pt-BR`), para leitores de tela escolherem a voz certa.
- `src/test/setup.ts` importa `@/i18n` e fixa `pt-BR` num `beforeAll` (o happy-dom se apresenta como navegador em inglês), e `.storybook/preview.tsx` também fixa `pt-BR`; um teste que troque o idioma deve restaurá-lo depois (ver `AppShell.test.tsx`/`LanguageSwitcher.test.tsx`).

### `src/services/` guarda as chamadas a APIs externas

`src/services/<serviceName>/` segue o mesmo formato de pasta por módulo que `src/utils/` (`<serviceName>.ts` + `index.ts` reexportando-o, ex.: `export * from "./viaCep"`), reexportado por sua vez através do `src/services/index.ts` no topo. Apenas named exports, nunca export default. **Diferente de toda outra camada deste projeto, services não recebem testes unitários** — não há `<serviceName>.test.ts` para escrever, nem mockado nem de outra forma (`httpClient` é a única exceção, justamente por não ser uma chamada de rede simples — ver abaixo).

**`src/services/organization/` é a camada da tela da Minha Organização** (organização atual, identidade visual e unidades), toda ligada ao backend. Ela nasceu com as assinaturas finais (`config?: RequestConfig` incluso) respondendo de dados em memória, e cada chamada foi trocada pelo backend sem mexer na página: é o caminho para uma tela nova cujo endpoint ainda não existe (um mock assim mostra o overlay global com `startLoading`/`stopLoading`, respeitando `showLoading`). Os tipos em `src/models/organization/` são o formato do frontend (`institutionalName`, `address.postalCode`, `address.country` como código ISO...), não o do backend (`orgInstName`, `orgAddressCep`, país em texto livre): integrar é trocar o corpo dessas funções por chamadas ao `httpClient` que convertem os campos, sem mexer na página. A integração é feita uma chamada por vez: **a organização já vem do backend** (`getCurrentOrganization` lê `GET /api/organizations/current/editable` e `updateOrganization` salva o nome institucional, o nome de exibição (`orgName`, editado em Dados institucionais, não na identidade visual), os contatos, o endereço e a observação interna em `PUT /api/organizations/current`, com o `version` lido por último; **esse `PUT` substitui todos os campos editáveis pelo que vier no corpo (um campo ausente vira `null`)**, então todo salvamento envia todos eles, os que a seção não mudou exatamente como o backend os devolveu por último (inclusive o país, que nenhum formulário edita); num 409 a página relê a organização e a seção mantém o rascunho, ver acima; um 404 na leitura é organização ainda não cadastrada, um estado próprio, diferente do erro de carga). O endereço tem cidade (`orgAddressCity`) e número como texto, a observação é `orgNotes` (até 2000), e os limites dos campos de endereço do backend valem também no formulário de unidade (`addressMaxLengths` em `MyOrganization.constants.ts`); o modelo de operação não é editável no backend, então fica só na leitura. **A identidade visual também já vem do backend**: `getBranding` lê o rascunho (`GET .../current/branding`) e `updateBranding` faz, num só "Salvar e publicar", as três chamadas do backend (salva o rascunho com o `orgName` como `displayName`, que o backend exige numa cópia própria; envia o logo e o favicon, se houver; publica com o `version` mais recente), guardando a resposta de cada passo para uma nova tentativa depois de uma falha no meio partir do `version` certo. As imagens seguem as regras do backend, conferidas na tela antes de enviar: o logo é PNG/JPEG, até 2 MB, de 64 a 2048 px de largura e de altura, proporção até 4:1; o favicon é PNG/JPEG (sem `.ico` nem SVG), até 512 KB, **quadrado** (largura igual à altura), de 16 a 512 px. Uma imagem maior que o máximo é reduzida na própria tela (num canvas, mantendo a proporção e avisando) antes de ir para o backend; o resto do que ele recusaria é recusado na tela, uma cor primária que deixa o texto branco abaixo do contraste WCAG AA (4,5:1, via `getContrastRatio` de `@/utils/colors`) ganha um aviso, sem impedir a publicação, o cabeçalho da Visão geral mostra o logo e o favicon **publicados**, e os links de imagem valem 5 minutos (nunca guarde um). O envio de logo e favicon depende do armazenamento de arquivos do backend (B2) estar ligado; desligado, responde 503. **As unidades também**: `listSchoolUnits` lê todas as páginas de `GET /api/school-units`; `createSchoolUnit` e `updateSchoolUnit` enviam o endereço estruturado (o backend monta dele a cópia em texto único; o logradouro é obrigatório para o endereço valer como estruturado), o e-mail e o telefone obrigatórios (o telefone no formato internacional) e as observações (`unitNotes`), a edição com o `version` da unidade; `getSchoolUnitInactivationImpact` lê os usuários vinculados (`deactivation-check`) e `inactivateSchoolUnit` inativa com motivo, o `version` lido e a confirmação do impacto. Uma unidade de antes do endereço estruturado vem com os campos vazios e o texto antigo em `legacyAddress`, mostrado como está e como referência ao editar. Reativar existe no backend (`activateSchoolUnit`), mas não na tela (DP-P1-06). **Os erros de unidade vêm com um código estável** (`ApiErrorCode`, lido com `getErrorCode(error)` de `@/services/httpClient`): `UNIT_NAME_DUPLICATE` mostra a mensagem do nome repetido e mantém o formulário, `VERSION_CONFLICT` relê a lista e mantém o diálogo com o rascunho (fecha só se a unidade foi inativada por outra pessoa); um cadastro sem resposta (timeout, conexão caída) relê a lista e, se a unidade com aquele nome estiver nela, conta como cadastrado, senão pede para conferir a lista antes de tentar de novo, para não gerar duplicata; nunca decida pelo texto da mensagem. A aba Unidades é dona das próprias ações (`units/useUnitActions.ts`) e só devolve à página a lista alterada, que o resumo da Visão geral também mostra. No E2E todas as chamadas são simuladas com `page.route`, cada mock guardando o que foi salvo como o backend faz (a lista vazia é uma resposta vazia). Uma página importa um service da própria pasta (`@/services/organization`), não do barrel, como as páginas no roteamento.

**Há um service por área do Swagger, com uma função por endpoint** (conferido contra o `docs/openapi.json` e o `docs/P02_CONTRATO.md` do repositório do backend no commit `3fe4ded`, 2026-11-18, igual ao Swagger publicado: corpos tipados, sem o usuário logado como parâmetro, a matriz v2.0 publicada em `/api/access-matrix` (Admin e Secretaria) e `/api/me/capabilities`, e a edição de nome e telefone em `/api/users/{id}/profile` e `/api/me/profile`): `auth` (inclui o limite de sessões e o aceite de convite), `organizations`, `schoolUnits`, `branding`, `organizationFiles`, `screenPreferences` (legado), `userAccounts` (legado), `audit`, `me`, `users`, `invitations` e `accessMatrix`, e os da P03 (conferidos contra o `docs/P03_CONTRATO.md` no `b810438`): `people` (pesquisa, checagem, revisão de duplicidade, documentos e LGPD), `students`, `guardians`, `studentGuardianLinks` e `catalogs`, e os da P04 (conferidos contra o `docs/P04_CONTRATO.md` e o OpenAPI no `61c4178`): `academicPeriods`, `academicCatalog`, `academicClasses`, `academicClassDetail` e `academicCalendar`, e o da P05 (`docs/P05_CONTRATO.md`, no `1f7b763`): `enrollments`, cada um com os tipos em `src/models/<mesma pasta>/` nos nomes do backend (`orgInstName`, `ApiOrganization`...; os do frontend, `Organization`/`SchoolUnit`, ficam em `models/organization`). **`services/organization` é a camada da tela**, que responde no formato do frontend sobre esses (a organização, a identidade visual e as unidades). Cada função traz um comentário `USED` ou `NOT USED YET` dizendo se alguma tela a chama, mais os códigos de erro que o Swagger documenta; **ao ligar uma tela a um endpoint, troque o comentário**. `unwrapApiResponse` (de `@/services`) tira o `data` do envelope e `toFileFormData` monta o corpo de um upload (multipart, campo `file`). Os endpoints que o Swagger deixa sem tipo (a lista de unidades e o consolidado vêm como "objeto") são tipados pela descrição. O usuário logado vem sempre do token: nenhuma chamada manda um `actor`/`user` (o Swagger antigo os mostrava por engano; os de usuário legados, `admin/users/...`, recebem só o próprio corpo). Não há função para o cadastro antigo (`/api/auth/register`) nem para a criação de escola (`/api/tenants/register` e `/api/platform/tenants`): conta nasce de convite, e escola é criada pela equipe JLM fora do app. O backend aceita `direction` em minúsculas (`asc`/`desc`) e recusa `organizationId` na lista de unidades. O Swagger documenta os uploads como `application/json`, mas as descrições dizem `multipart/form-data`.

### Ambiente, proxy de desenvolvimento e CORS

- A URL do backend vem de `VITE_API_BASE_URL` (tipada em `src/vite-env.d.ts`). O `.env` (versionado, só valores públicos; segredos vão num `.env.local` ignorado pelo git) aponta para o backend no Render, e é o que o build de produção usa: o app chama o backend direto, então **o backend precisa liberar as origens do app no CORS** — os endereços das escolas, `https://*.schoolflow360.com.br`, na variável `CORS_ALLOWED_ORIGIN_PATTERNS` do serviço do backend — sem isso o navegador bloqueia toda chamada, inclusive o login.
- Em desenvolvimento, o `.env.development` deixa `VITE_API_BASE_URL` vazio: o app chama `/api` na própria origem e o `server.proxy` do `vite.config.ts` encaminha para `API_PROXY_TARGET` (sem prefixo `VITE_`, então não vai para o navegador), removendo o header `Origin`. Assim o desenvolvimento local não depende do CORS do backend. O `vite preview` reaproveita o mesmo proxy.
- **O backend é multi-tenant (uma base por escola) e exige o header `X-Tenant-ID` em toda chamada, inclusive o login** — sem ele procura no tenant `public` e recusa contas válidas (401). **Cada escola tem o próprio endereço**, sob o domínio da plataforma (`VITE_TENANT_DOMAIN`, no `.env`: `schoolflow360.com.br`): o primeiro trecho do endereço é a escola, com `-` onde o tenant tem `_` (`colegio-saber.schoolflow360.com.br` é o `colegio_saber`). `getTenantId()` (`src/utils/tenant/`) lê o tenant do endereço; o próprio domínio, um nome reservado (`www`, `app`, `api`), mais de um nível ou um nome que o backend recusaria (só `a-z`, `0-9` e `_`, até 63) não servem escola nenhuma. Qualquer outro endereço (`localhost`, o do Render) serve o `VITE_TENANT_ID` fixo, que só o `.env.development` define (`schoolflow_demo`, para o desenvolvimento e o E2E): **em produção, um endereço sem escola não serve nenhuma**. Um endereço sem escola vai para `/unknown-school` (`paths.unknownSchool`, página `UnknownSchool`, fora do `AppShell`), que diz que o endereço não é de uma escola e mostra o formato do endereço de uma; os `loader`s do login, da recuperação de senha, da troca de senha e do `AppShell` mandam para lá, e ela manda para o login um endereço que serve escola. **Um endereço com cara de escola que o backend não conhece** (404 `TENANT_NOT_FOUND`, em qualquer chamada feita com o tenant do endereço) leva o `httpClient` a recarregar o app em `/school-not-found` (`paths.schoolNotFound`, página `SchoolNotFound`, na pasta do `UnknownSchool`, via `showSchoolNotFound` de `src/utils/authRedirect/`): "Escola não encontrada", com o endereço aberto para conferir e "Tentar de novo", diferente de uma falha do servidor; uma chamada com o tenant de um link de e-mail (`tenantId` no `RequestConfig`) fica para a página tratar, como um link morto. **Uma escola desativada** (a equipe JLM a desativa no banco, sem endpoint; ver o `docs/NOVO_CLIENTE.md` do backend, `268f416`) recusa toda chamada com 403 `ORGANIZATION_INACTIVE`, inclusive o login, a identidade pública e os links dos e-mails, e nem o Admin entra: o `httpClient` recarrega o app em `/school-inactive` (`paths.schoolInactive`, página `SchoolInactive`, na pasta do `UnknownSchool`, via `showSchoolInactive` de `src/utils/authRedirect/`), "Escola desativada", com "Tentar de novo" para quando ela for reativada (o backend percebe em cerca de 20 segundos). Diferente do `TENANT_NOT_FOUND`, vale também para uma chamada com o `tenantId` de um link: nada da escola funciona. **O login e a recuperação de senha abrem o cartão com o logo e o nome que a escola publicou** (`SchoolIdentity` + `usePublicBranding`, de `src/pages/shared/school/`, sobre o `GET /api/public/branding`, aberto sem token e lido sem o overlay): enquanto lê, sem nada publicado (404 `BRANDING_NOT_PUBLISHED`) ou numa falha, a tela fica com a aparência padrão e nunca espera por ele; é essa leitura que descobre, logo ao abrir o login, uma escola que não existe. O link do logo vale 5 minutos: é mostrado, nunca guardado, e um logo que não carrega some, ficando o nome. **Depois do login, o app mostra a identidade publicada da escola**:

- O `useSchoolBranding` (de `@/hooks`) lê o `GET .../branding/published`. A resposta fica só em memória e é relida a cada montagem, porque os links de imagem valem 5 minutos (só as cores ficam guardadas, ver abaixo).
- **Enquanto a identidade não foi lida, o topo do menu mostra blocos de carregamento** (prop `brandLoading` do `Sidebar`, pelo `useSchoolBrandingSettled` de `@/hooks`), não o nome e o ícone do produto, que os da escola trocariam um instante depois. Uma leitura que falha também encerra a espera, e aí fica o visual do produto.
- O menu lateral mostra o favicon da escola (quadrado, cabe no espaço do ícone, inclusive no menu recolhido) ou, sem ele, o logo, o nome da escola e um "Powered by SchoolFlow360º" discreto (prop `subtitle` do `Sidebar`).
- A aba do navegador mostra "Página · Escola" com o favicon da escola (`setDocumentIdentity`, de `src/utils/documentIdentity/`). O login e a recuperação de senha fazem o mesmo pela identidade pública (`useSchoolDocument`).
- Publicar na Minha Organização chama o `refreshSchoolBranding`, e o menu muda na hora.
- Sem nada publicado fica o visual do produto.
- **A cor primária da escola pinta a interface** (botões, links, foco dos campos, aba e item do menu ativos (texto e ícone), iniciais do avatar, página atual da paginação, checkboxes): `applySchoolColors` (`src/utils/theme/`) monta a escala de dez passos com `buildPrimaryScale` e a põe nas variáveis `--sf-primary-<passo>` do `<html>`, que o `colors.primary` lê. A cor fica no passo de luminosidade mais próximo da paleta do produto, e os passos de texto mantêm o WCAG AA (o 600 contra o branco, o 700 contra o fundo do item ativo), escurecidos quando a cor não chega lá. O `AppShell` a aplica pela identidade publicada, e o login e a recuperação de senha pela pública (`useSchoolDocument`). A cor padrão do produto (`#00285B`) não liga nada. As cores semânticas (sucesso, erro, aviso, informação) nunca mudam.
- **A cor secundária fica só em detalhes** (`colors.accent[500]`, a variável `--sf-accent-500`: o ponto do subitem ativo do menu e o anel interno do carregamento), nunca em texto nem em fundo sob texto; escurecida até 3:1 contra o branco (`buildAccent`), e sem ela o acento segue o primary 500.
- **O fundo das páginas depois do login** (o `AppShellContent`) é o cinza claro com 5% da cor da escola (o passo 500 da escala, por `buildPageBackground`), em `colors.page.background` (`var(--sf-page-background, <neutral 50>)`): o bastante para dar o tom da escola, pouco o bastante para os cartões brancos e as cores de situação continuarem como no cinza. Sem cor de escola, o cinza de sempre.
- **O fundo animado das telas antes do login** (o do `body`, no `GlobalStyle`) é desenhado em CSS, sem imagem: um azul-marinho com três brilhos suaves (azul no canto superior esquerdo, verde-azulado no superior direito, azul vindo do inferior direito), ampliados e deslizando devagar. As cores vêm de `colors.backdrop` (`var(--sf-backdrop-<nome>, <hex do produto>)`, com os hex em `backdropPalette`, `src/foundation/backdropPalette.ts`), e `buildBackdrop` (`src/utils/theme/`) as refaz no tom da escola: cada uma mantém a luminosidade do produto e ganha o matiz da primária (o brilho verde-azulado, o da secundária), nunca mais saturada que a do produto, para não gritar. Sem cor de escola (ou com a padrão), as variáveis ficam vazias e o fundo é o do produto.
- **As cores aplicadas ficam guardadas no navegador** (`sf360.schoolColors` no `localStorage`, só as duas cores: nada da pessoa nem os links de imagem), e o `main.tsx` as pinta antes da primeira renderização (`restoreSchoolColors`), para a próxima visita não piscar a cor do produto antes. Por isso `useSchoolBranding` e `usePublicBranding` distinguem `undefined` (ainda não lida, ou não pôde ser lida: as cores guardadas ficam) de `null` (nada publicado: volta à cor do produto e esquece as guardadas).
- No Storybook, a ferramenta **Cor da escola** da barra (`.storybook/SchoolColorTheme.tsx`) pinta as stories com cores de exemplo, e a página `Foundation/Cor da escola` (`src/foundation/SchoolColors.mdx`) explica o tema e mostra as escalas geradas.

No E2E, o `test` de `e2e/support/test.ts` responde que nada foi publicado, nas duas rotas. As páginas abertas pelos e-mails (redefinição de senha e aceite de convite) trazem a própria escola no link (`?tenant=`) e abrem em qualquer endereço; quando o endereço aberto não é o daquela escola (o do Render, ou o de outra), o "ir para o login" e os outros links delas levam ao endereço próprio da escola (`SchoolLink` e `useGoToSchool`, de `src/pages/shared/school/`, sobre o `getSchoolAddress`). Cada endereço guarda a própria sessão (o `localStorage` é por origem). O CORS do backend já libera `https://*.schoolflow360.com.br`; cada escola nova precisa de um CNAME no Registro.br e do domínio cadastrado no Render (o roteiro é o `docs/NOVO_CLIENTE.md` do backend).

- Toda resposta do backend vem no envelope `ApiResponse<T> = { data, message, status, tenantId, code? }` (o `code` só em alguns erros) (`src/models/httpClient/`); um service desembrulha o `data` antes de devolver (ver `login` em `src/services/auth/`).

### `src/services/httpClient/` e o overlay global de Loading

Todo service **deve** chamar a API através do `httpClient` compartilhado (`src/services/httpClient/httpClient.ts`, reexportado via `@/services`) em vez de importar o `axios` diretamente (ver `viaCep.ts`) — seus interceptors de request/response são o que faz o overlay `Loading` (`src/components/Loading/`) aparecer automaticamente em toda chamada de API, sem nenhuma conexão manual por ponto de chamada:

- `GlobalLoading` (`src/components/GlobalLoading/`) é montado uma única vez em `main.tsx`, junto com o router. Ele assina `src/utils/loadingStore` (um contador simples de requisições pendentes, com um par subscribe/notify, testado unitariamente como qualquer outro util) via `useSyncExternalStore`, e renderiza `<Loading />` sempre que esse contador estiver acima de zero, **por cima de qualquer elemento da tela**, modais e seus menus inclusive (camada própria, `zIndex.loading`, a mais alta da foundation). Se a mesma espera passar de 5s, o overlay mostra uma mensagem abaixo do spinner (prop `message` do `Loading`). Ela só culpa o servidor (`common.slowServer`, "Conectando ao servidor...") quando é provável que o backend esteja acordando: ele fica, por enquanto, num plano do Render que hiberna após 15 minutos sem tráfego, e `src/utils/backendActivity` guarda (por aba, em memória) quando ele respondeu pela última vez, marcado pelos interceptors do `httpClient`. Fora disso, uma chamada demorada recebe a mensagem neutra `common.slowWait` — uma chamada lenta não significa servidor fora do ar.
- Os interceptors do `httpClient` chamam `startLoading()`/`stopLoading()` em toda request/response (ou erro) — essa é a única conexão entre uma chamada de API e o contador, então um novo service ganha o overlay automaticamente de graça só por usar o `httpClient`.
- Os interceptors também cuidam da autenticação: toda chamada com URL relativa (o nosso backend, via `baseURL`) recebe o `X-Tenant-ID` e o `Authorization: Bearer <token>` da sessão; uma URL absoluta (uma API de terceiros, como o ViaCEP) nunca recebe o token. **A sessão se renova sozinha**: o token de acesso dura 1 h e o de renovação 7 dias (e muda a cada renovação), então uma chamada com o token de acesso vencido é precedida por `renewSession()` (`POST /api/auth/refresh`, sem `Authorization`; chamadas simultâneas dividem uma só renovação, guardando o `context` de antes), e um 401 numa chamada que levou token renova uma vez e manda a chamada de novo. Só quando o backend recusa a renovação a sessão acaba: `endExpiredSession` (`src/utils/authRedirect/`) limpa a sessão e recarrega o app em `/login?redirect=<página atual>&expired=1`; um backend fora do ar não encerra a sessão. O `AppShell` renova no horário do `expiresAt` via `useSessionExpiry`, mesmo com a página parada; o "Sair" do menu do usuário no topo (`AppShell`; o bloco com nome e papéis abre esse menu, via `userMenuItems` do `Topbar`; nome e papéis vêm do loader da rota, ver Roteamento) só navega para `/sign-out` (`paths.signOut`), uma rota sem página cujo `loader` apaga a sessão, redireciona para `/login` e só depois avisa o backend (`logout(token, { showLoading: false })`, importado sob demanda para o axios não entrar no chunk inicial, e que recebe o token explicitamente porque a sessão já foi apagada), sem esperar a resposta — ser uma navegação é o que faz o "Sair" passar pelo aviso de alterações não salvas; um 401 sem token (senha errada no próprio login) fica para quem chamou tratar. Para separar esses casos numa página sem importar o axios, use `getErrorStatus(error)`, exportado de `@/services` (`undefined` quando não houve resposta: rede fora, CORS, timeout). Quando dois erros dividem o mesmo status (um 409 de versão desatualizada e um 409 de nome repetido), use `getErrorCode(error)`, que devolve o `code` estável do envelope (`ApiErrorCode`, em `src/models/httpClient/`) ou `undefined` quando o erro não tem um. `getErrorCorrelationId(error)` devolve o `correlationId` da chamada (do envelope, senão do header `X-Correlation-ID`), que a acha nos logs do backend: mostre-o como referência do suporte numa falha inesperada. `getErrorData(error)` devolve o `data` de um erro que traz um (o 409 `SESSION_LIMIT_REACHED` do login traz o desafio e as sessões), e `getRetryAfterSeconds(error)` o `Retry-After` de um 429, quando o navegador consegue lê-lo.
- A assinatura pública de toda função de service **deve** aceitar os argumentos próprios da requisição mais um parâmetro final e opcional `config: RequestConfig` (ex.: `getAddressByCep(cep: string, config?: RequestConfig)`), repassado diretamente como o segundo argumento do `httpClient`. `RequestConfig` (exportado de `httpClient.ts`) hoje é `Pick<AxiosRequestConfig, "idempotencyKey" | "onUploadProgress" | "showLoading" | "signal" | "tenantId">` — um objeto deliberadamente restrito e construído para esse propósito (não o `AxiosRequestConfig` completo) — então quem chama e não quer o overlay global para uma chamada específica passa `{ showLoading: false }`; qualquer outra coisa (inclusive omitir `config`) exibe o overlay. `tenantId` troca o `X-Tenant-ID` daquela chamada, para quando a própria requisição traz a escola (o link de redefinição de senha vem com `?tenant=`, ver `src/pages/ResetPassword/`); sem ele vale o `getTenantId()` do deploy. `idempotencyKey` vai como o header `Idempotency-Key`, para repetir um cadastro (duplo clique, nova tentativa depois de um timeout) devolver o primeiro resultado em vez de criar dois: gere uma chave por tentativa que o usuário entende como uma só. `onUploadProgress` acompanha um envio de arquivo (o progresso na tela) e `signal` (de um `AbortController`) cancela a chamada, para um envio que o usuário desiste de fazer (ver `useDocumentUpload`). Adicione novos campos à mesma augmentation `declare module "axios"` em `httpClient.ts` e inclua-os em `RequestConfig` via `Pick` conforme surgirem novas opções transversais por chamada, em vez de fazer crescer a lista de parâmetros de cada service individualmente.

### `src/models/` guarda os tipos de cada service

`src/models/<serviceName>/` espelha um a um a pasta do `src/services/<serviceName>/` correspondente (`<serviceName>.ts` + `index.ts` reexportando-o, ex.: `export * from "./viaCep"`, reexportado por sua vez através do `src/models/index.ts` no topo). Guarda todo tipo ligado aos endpoints daquele service — parâmetros de requisição, formatos de resposta (ver `ViaCepAddress` em `models/viaCep/viaCep.ts`) — de modo que o próprio arquivo do service só importa tipos de `@/models`, nunca declara os seus. Apenas named exports, nunca export default, e — assim como `src/services/` — sem testes unitários, já que são declarações somente de tipos, sem nada para executar.

### `src/foundation/` é a fonte única dos design tokens

`src/foundation/` define um sistema de tokens baseado em código (colors, spacing, typography, motion, radius, shadows, opacity, zIndex, breakpoints), exportado através de `src/foundation/index.ts`. É o único sistema de design tokens do projeto — novas UIs devem consumir valores de `src/foundation` dentro das definições de `styled-components` (ex.: `colors.primary[500]`, `spacing[16]`) em vez de fixar cores/espaçamentos/etc. diretamente no código. Note que atualmente não há variantes de dark mode.

**`colors.primary` segue a cor da escola**: cada passo é `var(--sf-primary-<passo>, <hex do produto>)`, com o hex de `brandPalette` (`src/foundation/brandPalette.ts`) como reserva, e `colors.accent[500]` segue a cor secundária (só para detalhes, ver Ambiente). Por isso um valor de `colors.primary` (e o `semanticColors.brand`) não é um hex: o `hexToRgba` o mistura com `color-mix`, e quem precisa do hex real (um teste, uma conta de contraste, a cor padrão da identidade visual) usa `brandPalette`. Num teste unitário, compare o fundo pela propriedade longa (`backgroundColor`, nunca `background`, que o happy-dom não resolve com `var()`) contra `brandPalette[passo]`.

`spacing` e `colors.primary`/`colors.neutral` são escalas com chaves numéricas, mas não significam a mesma coisa: as chaves de `spacing` são o próprio valor em pixels (`spacing[16]` é `"16px"`, `spacing[24]` é `"24px"`, ...), enquanto as escalas de cor usam números de passo abstratos (`colors.primary[500]` é o azul base da marca, não "500px" de nada). Não assuma que uma convenção de chave numérica se aplica às duas.

### Os componentes seguem o Atomic Design, dentro de `src/ds-components/`

Os componentes de UI ficam em `src/ds-components/<layer>/<ComponentName>/`, onde `<layer>` é uma de `atoms`, `molecules`, `organisms`, `templates` (páginas roteadas ficam em `src/pages/` — ver acima). Cada componente tem sua própria pasta em PascalCase contendo:

- `ComponentName.tsx` — o componente como named export (ex.: `export const Text = ...`) mais seu `export type ComponentNameProps`.
- `ComponentName.styles.ts` — as definições `styled-components`, importadas em `ComponentName.tsx`. Mantenha as declarações de estilo fora do próprio arquivo do componente.
- `index.ts` — barrel reexportando tudo do arquivo do componente, ex.: `export * from "./ComponentName"`.

Cada pasta de camada (`atoms/`, `molecules/`, ...) também tem seu próprio barrel `index.ts` reexportando todo componente daquela camada, ex.: `export * from "./Text"` (ver `src/ds-components/atoms/index.ts`) — adicione novos componentes a esse barrel também. **Dentro de `src/ds-components/` e `src/components/`, um componente importa outro da pasta dele (`@/ds-components/molecules/Input`), nunca dos barrels de `molecules`, `organisms`, `templates` ou de `@/components`** (o de `atoms`, leve, continua permitido; a regra `no-restricted-imports` do `eslint.config.js` barra o resto): fora de um bundle (testes unitários, servidor de dev) um barrel carrega todos os componentes da camada, e o de molecules arrasta PhoneInput, Select e DateInput junto. As páginas continuam importando dos barrels, já que no build o que não é usado é descartado.

`src/ds-components/atoms/Text/` é a implementação de referência: deriva suas variantes de `size`/`weight` diretamente de `typography.fontSize`/`fontWeight`/`lineHeight` e suas variantes de `color` a partir de um mapa semântico (`default`/`secondary`/`muted`/`inverse`/`brand`/`success`/`warning`/`danger`/`info`) apoiado em `colors` — siga esse padrão (valores de prop semânticos mapeados para tokens de `src/foundation`, não valores brutos em hex/px) para novos atoms/molecules/organisms.

Todo componente também aceita uma prop `style?: CSSProperties` (importada como `import type { CSSProperties } from "react"`), repassada diretamente ao elemento estilizado raiz (ex.: `<StyledText style={style}>`) como uma via de escape para estilo inline pontual, além das props de variante — ver `Text.tsx`/`Text.styles.ts`.

### `src/components/` guarda componentes que não fazem parte do design system ds-components

Diferente de `src/ds-components/`, `src/components/<ComponentName>/` é plano (sem o segmento `<layer>` do Atomic Design) e guarda componentes que não são feitos para ser peças reutilizáveis e documentadas do design system — o `Loading` (um overlay de tela cheia ligado a estados assíncronos no nível da aplicação) fica aqui. Ainda assim segue o mesmo formato de pasta por componente (`ComponentName.tsx` + `.styles.ts` + `index.ts` + `.stories.tsx` + `.test.tsx`) e as mesmas convenções (styled-components, tokens de `@/foundation`, props `style`/`className`, ordem alfabética de props via `eslint-plugin-perfectionist` — ver seu glob `files` em `eslint.config.js`, que cobre tanto essa pasta quanto `src/ds-components/`). Tem seu próprio barrel `src/components/index.ts` no topo, igual a qualquer outra camada.

### Campos de formulário: `FieldLabel`, `FieldMessage`, `error` e `required`

Todo campo (`Input`, `Textarea`, `Select`, `DateInput`, `FileUpload`, `ColorPicker`, `Checkbox`, `Switch`) segue o mesmo contrato, montado sobre dois atoms:

- `FieldLabel` renderiza o `title` como `<label htmlFor>`; com `required` adiciona um asterisco vermelho `aria-hidden` (quem anuncia o obrigatório é o `required`/`aria-required` do próprio campo).
- `FieldMessage` renderiza, abaixo do campo, o `error` quando há um (substituindo o `helperText`) ou o `helperText`, com `id` estável `${id do campo}-message`. As cores são `neutral[700]`/`danger[700]`, não os tons 500, porque só os 700 atingem o contraste WCAG AA nesse tamanho de fonte.
- O campo aponta `aria-describedby` para esse id (somado a um `aria-describedby` do próprio chamador, via `joinIds`), marca `aria-invalid` quando há `error` e pinta a borda de `danger[500]`.
- O `Input` também aceita `invalid`: borda vermelha e `aria-invalid` **sem** mensagem própria, para um erro que vale para vários campos e é explicado uma vez só (ex.: credenciais recusadas no Login, onde os dois campos ficam `invalid` e apontam `aria-describedby` para a mensagem única do formulário).
- O `Textarea` com `maxLength` mostra, enquanto tem foco, o contador `digitados/máximo` à direita da linha do texto de ajuda ou do erro, centralizado na altura dela e com um espaço do texto, que quebra de linha em vez de encostar nele (vermelho no limite; o contador fica sempre na linha, só escondido sem foco, para ela não mudar de tamanho), lendo o tamanho do próprio campo no foco e a cada alteração, então vale para um campo controlado e para um não controlado (`register` do react-hook-form); o limite em si é o `maxLength` nativo. Todo `Textarea` com limite ganha o contador, sem prop nova.
- Um campo novo deve seguir o mesmo contrato (props `error`/`helperText`/`required`, os dois atoms e os mesmos atributos ARIA), com stories `WithError`/`Required` e testes de `toHaveAccessibleDescription`/`aria-invalid`. Um campo sem `title` visível precisa de `aria-label` (o `Select` aceita `aria-label` para isso, ex.: dentro da `FilterBar`).
- **Telefone é sempre o `PhoneInput`** (decisão de produto): um só campo, com um rótulo e uma mensagem, que junta à esquerda o seletor do país (o DDI: fechado mostra a bandeira e o código, `+55`, com o nome do país ao passar o mouse e a largura do tamanho do código, que desliza ao trocar de país; a busca do seletor é marcada para os gerenciadores de senha a ignorarem, e o número leva `autocomplete="tel-national"`; aberto, todos os países com a bandeira, o nome no idioma da pessoa e o código, com busca pelo nome ou pelo código) e à direita o número. O país começa como o de quem usa o campo, tirado dos idiomas do navegador (`detectCountry`, de `@/utils/countries`: `pt-BR` é o Brasil, `pt` sem região também; nenhum serviço externo é consultado), a menos que o valor já tenha um número ou que a página passe `defaultCountry` (a Minha Organização passa o país da organização). O número segue o país como uma máscara: formatado como ele escreve, nunca mais longo que o maior número dele (`fitPhoneDigits`) e com um número de exemplo do país como placeholder (`getPhoneExample`; por isso as páginas não passam um placeholder próprio, a exceção à regra abaixo); escolher outro país limpa o número, e colar um número com `+` e o código troca o país sozinho. As bandeiras são SVGs da `country-flag-icons` (bandeira em emoji não aparece no Windows), num pedaço do bundle à parte carregado uma vez quando o primeiro telefone aparece. O valor que entra e sai é sempre o número inteiro no formato internacional (`+55 85 3333 1100`, ou vazio), o mesmo que vai para o backend, então um formulário o guarda como está, valida com `isValidPhone` e inicia com `toInternationalPhone` do que o backend devolveu. Os textos próprios (`countryLabel`, `noOptionsMessage`) e o idioma dos países (`language`) vêm, numa página, do `usePhoneInputTexts` (`src/pages/shared/phone/`), espalhado no campo (`{...phoneTexts}`); o texto de ajuda dos telefones diz para escolher o país antes.
- **O menu aberto de um `Select` mostra no máximo cinco opções** (decisão de produto), e o resto rola: a altura padrão (`getMenuMaxHeight`, em `Select.styles.ts`) é a de cinco opções do tamanho do campo, calculada pelos mesmos tokens das opções (o `medium` dá 208 px, o `small` 193 px). A prop `maxMenuHeight` continua existindo para um caso que peça outro valor.
- **Todo campo tem placeholder** (decisão de produto): todo `Input`, `Textarea`, `DateInput` e `Select`, nas páginas e dentro dos componentes, recebe um `placeholder`. Numa página ele é traduzido, com uma chave `<campo>Placeholder` ao lado do rótulo, na seção da página (ex.: `passwordChange.newPlaceholder`); uma data usa `common.datePlaceholder`. Um filtro cuja opção vazia é "Todos..." usa o rótulo dessa opção como placeholder. O placeholder não substitui o `title`, que continua sendo o nome acessível do campo. A única exceção é um campo só de leitura que sempre mostra um valor, como a senha temporária gerada.

### `Tooltip` e a convenção da prop `tooltip`

`src/ds-components/atoms/Tooltip/` fornece o balão de tooltip — **por padrão ancorado no próprio elemento**, com a opção de seguir o cursor — além do hook `useTooltip`, que qualquer componente usa para aderir a uma prop `tooltip?: string`:

- `Tooltip.tsx` é o balão apresentacional (`role="tooltip"`) — recebe `children` e a posição: `anchorRect` (a caixa do elemento, de `getBoundingClientRect`), que o centraliza abaixo dele, abre acima quando não há espaço embaixo e o mantém dentro da tela (medido num `useLayoutEffect`, escondido até ser posicionado), ou `x`/`y` (coordenadas do cursor), que o põe logo depois do ponteiro. Renderiza via `createPortal(..., document.body)` para não ser cortado por ancestrais com `overflow: hidden` e para sempre ficar acima do resto do conteúdo (`zIndex.tooltip`). Não tem lógica própria de visibilidade/hover — sempre renderiza quando montado.
- `useTooltip(tooltip?: string, options?: { anchor?: "element" | "cursor" })` (em `useTooltip.tsx`, co-localizado com `Tooltip` por ser fortemente acoplado a ele — note a extensão `.tsx`, necessária porque o hook retorna JSX) é o dono do estado de visibilidade/posição e retorna `{ tooltipElement, tooltipHandlers }`. Com `anchor: "element"` (o padrão, e o que toda prop `tooltip` usa) os handlers são `onMouseEnter`/`onMouseLeave`/`onFocus`/`onBlur` — também aparece no foco por teclado; com `anchor: "cursor"` são `onMouseEnter`/`onMouseMove`/`onMouseLeave`, só com o mouse. Sem texto de `tooltip` o hook não devolve handler nenhum, para não sobrescrever os do chamador. `tooltipHandlers` é espalhado no elemento estilizado raiz do componente; `tooltipElement` é o `<Tooltip>` já construído (ou `null` quando não há hover / nenhum texto de `tooltip` foi passado) para ser renderizado como irmão.
- Para adicionar isso a um novo componente: adicione `tooltip?: string` às suas próprias props (na posição alfabética entre as props opcionais), chame `const { tooltipElement, tooltipHandlers } = useTooltip(tooltip)`, espalhe `{...tooltipHandlers}` no elemento estilizado raiz (depois de `{...rest}`, para que sempre prevaleça sobre qualquer prop de mesmo nome repassada por quem chama), envolva o retorno em um fragment, e renderize `{tooltipElement}` como irmão depois do elemento raiz — ver `Text.tsx` para a conexão de referência.

### Estilização com `styled-components`

- Arquivos `.css` puros não são mais usados em nenhum lugar de `src/` — escreva todos os estilos com `styled-components`.
- Os styled components específicos de cada componente ficam em `ComponentName.styles.ts`, não inline no arquivo `.tsx`.
- Props passadas a um styled component que existem puramente para controlar CSS (não são atributos DOM válidos) devem usar o prefixo transitório `$` (ex.: `$size`, `$color`) para que o `styled-components` não as repasse ao nó do DOM — ver `Text.styles.ts`.
- A renderização polimórfica de tag (ex.: a prop `as` do `Text`) deve se apoiar no suporte nativo à prop `as` do próprio `styled-components`, em vez de trocar o elemento renderizado manualmente. Para ter os atributos próprios da tag renderizada tipados e repassados (ex.: `href` quando `as="a"`), torne as props do componente genéricas sobre `C extends ElementType` — as props próprias ficam em um tipo `TextOwnProps<C>`, e o `TextProps<C extends ElementType = "p">` exportado o intersecta com `Omit<ComponentPropsWithoutRef<C>, keyof TextOwnProps<C>>`. O próprio componente vira `<C extends ElementType = "p">(props: TextProps<C>) => {...}`, desestruturando as props conhecidas mais `...rest` e espalhando `rest` no elemento estilizado. Ver `Text.tsx`. (Um genérico solto como `<T>(props) => ...` é ambíguo com JSX em um arquivo `.tsx` e precisa de uma vírgula final — `<T,>` — ou de uma cláusula `extends` para desambiguar; como esse genérico já tem `extends ElementType`, a vírgula final não é necessária aqui.)
- Estilos globais/de reset ficam em `src/styles/GlobalStyle.ts` via `createGlobalStyle`, renderizado uma única vez em `main.tsx`.
- **O visual das barras de rolagem é global** (`GlobalStyle.ts`, seletor `*`): fina, com thumb translúcido de `neutral[900]` e trilho transparente. Não declare `scrollbar-width`/`scrollbar-color`/`::-webkit-scrollbar` em `*.styles.ts` — o componente só decide _onde_ rola (`overflow`), nunca _como a barra parece_. As duas famílias de regra existem de propósito: as propriedades padrão (`scrollbar-width`/`scrollbar-color`) valem para Firefox e Chrome/Edge 121+, que ignoram `::-webkit-scrollbar` quando qualquer uma delas está definida; as regras `::-webkit-scrollbar*` cobrem Safari e Chromium antigo.
- **Valores de token nos estilos devem usar os tokens de `src/foundation`, nunca literais fixos no código.** Toda propriedade CSS cujo valor tenha um token correspondente na foundation deve referenciar esse token — nunca escreva o valor bruto diretamente em um arquivo `.styles.ts` ou em um objeto `style={{...}}`:
  - Medidas em pixel → `spacing` (ex.: `padding: ${spacing[24]}`, `gap: ${spacing[8]}`)
  - Opacidade → `opacity` (ex.: `opacity: ${opacity.disabled}` em vez de `opacity: 0.5`)
  - Outros tipos de token seguem a mesma regra: `radius`, `shadows`, `colors`, `zIndex`, `typography`, `motion`, `translucency`
  - Exceções: valores sem token correspondente (bordas de `1px`, unidades de porcentagem/viewport, valores computados dinamicamente) e valores já derivados de outro token (ex.: `${typography.fontSize.sm}px`).

### Adicionando ou alterando props

Sempre que uma nova prop é adicionada a um componente (ou uma prop existente é alterada ou removida), dois arquivos **devem** ser atualizados na mesma mudança:

1. **`ComponentName.stories.tsx`** — adicione ou atualize a entrada de `argTypes` da prop (com o tipo de `control` e `description`) e adicione uma story dedicada que exercite o novo comportamento, caso ainda não esteja coberto.
2. **`ComponentName.test.tsx`** — adicione ou atualize os casos de teste que cobrem o comportamento da nova prop.

Isso não são follow-ups opcionais: documentação e testes fazem parte da mesma unidade de trabalho que a própria prop.

### Todo componente é documentado com Storybook

Cada pasta de componente também recebe um `ComponentName.stories.tsx` co-localizado (formato CSF3), junto com `ComponentName.tsx`/`.styles.ts`/`index.ts` — ver `Text.stories.tsx`. Convenções:

- O `title` no `meta` da story espelha o caminho do Atomic Design, ex.: `"Atoms/Text"`.
- `tags: ["autodocs"]` no `meta`, para que o Storybook gere a página de docs automaticamente a partir de `argTypes`/props, em vez de exigir um `.mdx` escrito à mão.
- Apenas dois addons do Storybook estão instalados: `@storybook/addon-docs` (autodocs) e `@storybook/addon-a11y` (checagens de acessibilidade), configurados em `.storybook/main.ts`. **Não adicione addons `@storybook/addon-vitest`/Chromatic/MCP** sem pedido explícito — o `storybook init` inclui esses por padrão, mas eles trazem junto os binários de navegador do Vitest + Playwright puramente para testes de componente, o que está fora do escopo (não há test runner de componentes neste projeto).
- `.storybook/preview.tsx` envolve toda story em `<GlobalStyle />` (de `src/styles/GlobalStyle.ts`) via um decorator, para que as stories renderizem com o mesmo reset da aplicação real.
- Toda story exportada (incluindo `Default`) recebe um comentário de uma linha logo acima descrevendo o que ela demonstra, ex.: `// The elevated prop adding a drop shadow and removing the border` — descreva a prop/comportamento/variante mostrada, não apenas repita o nome da story.
- **Este design system é voltado a um produto em português do Brasil (pt-BR)** — o conteúdo de exemplo renderizado pelas stories (valores de `args` como `children`/`title`/`placeholder`/`helperText`, e qualquer texto fixo dentro de um `render()` customizado) deve ser escrito em pt-BR, ex.: `title: "E-mail"`, `placeholder: "Digite algo..."` (ver `Input.stories.tsx`). Isso **não** se estende às strings de `argTypes[...].description`, aos comentários de story, nem a nada mais no código — esses permanecem em inglês, como o resto do código. Também não traduza valores que fazem parte, literalmente, da superfície de API do componente (ex.: `color="default"`/`color="brand"` demonstrados renderizando o próprio nome do token, ou o slug `name` de um `Icon`) — traduzir esses faria o rótulo exibido mentir sobre o valor real da prop.
- **O Storybook publicado (`https://school-flow-360-storybook.web.app`) é atualizado pela esteira** (ver "CI/CD com GitHub Actions" abaixo): todo merge no `master` o republica, e todo PR ganha um preview dele com as mudanças. É assim que o time revisa os componentes fora do código. `bun run deploy-storybook` continua existindo para uma emergência, mas não é mais um passo do dia a dia.

### Testes unitários com Vitest + React Testing Library

- Cada pasta de componente também recebe um `ComponentName.test.tsx` co-localizado — ver `Text.test.tsx`. Teste o comportamento renderizado (conteúdo de texto, nome da tag, atributos/classes) via `render`/`screen` do `@testing-library/react`, não detalhes de implementação.
- O Vitest é configurado diretamente em `vite.config.ts` (`test: { environment: "happy-dom", exclude: [...], pool: "threads", setupFiles: ["./src/test/setup.ts"] }`) — não há um `vitest.config.ts` separado. O ambiente é o **happy-dom**, não o jsdom: a suíte roda ~30% mais rápido. Ele devolve alguns estilos calculados em outra forma (`transparent` em vez de `rgba(0, 0, 0, 0)`, `0` em vez de `0px`, a borda pelas propriedades separadas e não pelo atalho `border`), então um `toHaveStyle` confere as propriedades longas; e tem `matchMedia` e `ResizeObserver`. O E2E no Chromium continua sendo o que confere o navegador de verdade. O `pool: "threads"` roda os arquivos em threads, que sobem mais rápido que os processos do padrão, e cada arquivo continua isolado. Não desligue o isolamento (`isolate: false`): ele deixa a suíte bem mais rápida, mas mocks e estado de um arquivo vazam para outro (`useSessionExpiry`, `storage`). A tipagem do campo `test` vem do `import { configDefaults } from "vitest/config"` (também usado para estender a lista padrão de exclusões e ignorar `e2e/**`, ver a seção sobre Playwright abaixo), não mais de uma diretiva triple-slash — o `eslint-plugin-typescript-eslint` rejeita `/// <reference ... />` quando o mesmo módulo já é importado normalmente.
- `src/test/setup.ts` importa `@testing-library/jest-dom/vitest` (o entry point específico do Vitest, não o genérico `@testing-library/jest-dom`) para registrar matchers como `toHaveClass`/`toBeInTheDocument` no `expect` do Vitest.
- Importe `describe`/`it`/`expect` explicitamente de `"vitest"` em todo arquivo de teste — `globals` não está habilitado na configuração do Vitest, alinhado com a preferência deste projeto por imports explícitos em vez de globais ambientes.
- `@testing-library/dom` é uma peer dependency obrigatória de `@testing-library/react` e deve permanecer instalada mesmo que nada a importe diretamente.
- `src/test/setup.ts` também chama `afterEach(() => cleanup())` explicitamente. O auto-cleanup do React Testing Library só se registra sozinho quando detecta um `afterEach` global (ex.: Jest, ou Vitest com `globals: true`); como a configuração do Vitest deste projeto mantém `globals` desligado, o auto-cleanup nunca dispara sem isso — e sem ele, cada `render()` em um arquivo continua se acumulando em `document.body` entre os blocos `it` (mais visível em componentes baseados em portal, como `Tooltip`, ou em texto repetido entre testes).

### Testes E2E com Playwright

- `e2e/<fluxo>.spec.ts` guarda os testes de ponta a ponta, um arquivo por fluxo/página (ex.: `e2e/home.spec.ts`, `e2e/login.spec.ts`) — não é o mesmo diretório nem a mesma ferramenta dos testes unitários (`ComponentName.test.tsx` com Vitest + RTL, ver acima). Importe `expect`/`test` (e o tipo `Page`) de `"./support/test.ts"`, nunca de `"vitest"` nem direto de `"@playwright/test"`: esse `test` já simula o `/api/me` (um Admin, `signedInUser`) e recusa a renovação de sessão, para nenhuma spec chegar ao backend real pelo proxy do servidor de desenvolvimento (uma spec troca qualquer um com o próprio `page.route`, e a última rota registrada vence), e prefira locators por role/label (`page.getByRole(...)`, `page.getByLabel(...)`) em vez de seletores CSS/`data-testid`, na mesma linha do RTL usado nos testes unitários.
- `playwright.config.ts` (raiz) define `testDir: "./e2e"` e um `webServer` que, antes da suíte, faz o build do app em modo de desenvolvimento (`vite build --mode development --outDir dist-e2e`, ignorado pelo git) e o serve com `vite preview` na porta 5174. Os testes rodam contra esse build, não contra o servidor de dev: cada teste abre um navegador limpo, e o servidor de dev mandaria centenas de módulos soltos, compilando cada página no primeiro acesso, o que deixava a suíte lenta e instável. O modo de desenvolvimento lê o `.env.development` (a escola fixa `schoolflow_demo` e o `/api` na própria origem, que as specs simulam). Fora do CI um servidor já rodando na 5174 é reaproveitado (`reuseExistingServer`); como ele serve um build, uma mudança no código só entra na suíte depois de parar esse servidor. Não é preciso subir o servidor manualmente antes de `bun run e2e`. No CI a suíte roda com 3 workers (o runner tem 4 processadores) e 2 novas tentativas; localmente o Playwright escolhe o número de workers.
- `tsconfig.e2e.json` (espelhando `tsconfig.node.json`) cobre `e2e/` e `playwright.config.ts` no `tsc -b`, e o bloco de globals Node do `eslint.config.js` (originalmente só para `scripts/`) também cobre esses arquivos — ambos rodam em Node, não no browser.
- Os testes E2E cobrem fluxos reais de navegação/interação do usuário através de páginas inteiras (`src/pages/`) — não são um substituto para os testes unitários por componente, e não geram uma story nem alteram a regra de "Adicionando ou alterando props" (isso continua sendo Storybook + Vitest).
- `playwright.config.ts` fixa `locale: "pt-BR"`: o app detecta o idioma do navegador, e as specs são escritas contra o texto em pt-BR.
- Chamadas ao backend são simuladas no navegador com `page.route("**/api/...", ...)` (ver `e2e/login.spec.ts`), para a suíte não depender do backend estar no ar nem de credenciais reais.
- `playwright-report/`, `test-results/` e `blob-report/` (gerados por `bun run e2e`) são ignorados pelo git.

### Convenções de `src/foundation/`

Todo módulo de token segue o mesmo formato — siga-o ao adicionar um novo ou editar os existentes:

```ts
export const tokenName = { ... }
export type TokenNameType = typeof tokenName
```

- Apenas named exports — **sem `export default`**. O barrel (`src/foundation/index.ts`) reexporta tudo via `export *`, que não repassa export defaults, então um default seria código morto.
- Os exports do barrel são ordenados alfabeticamente por nome de arquivo; mantenha novos módulos nessa ordem.
- Os object literals não usam `as const` — os valores são ampliados para `string`/`number` nos tipos `*Type` derivados, em vez de manter tipos literais.
- `breakpoints.ts` é a única exceção à regra "um objeto + um tipo por módulo": exporta tanto `breakpoints` (valores brutos em pixels) quanto `media` (os mesmos valores já envolvidos em strings `(min-width: ...)`), cada um com seu próprio `BreakpointsType`/`MediaType`.
- **Cor de texto (e de fundo sob texto branco) deve atingir o contraste WCAG AA (4,5:1).** Por isso `semanticColors` usa `primary[600]` e os tons 700 (`danger`/`info`/`success`/`warning`, e `neutral[700]` para `muted` e `secondary`), não os 500 da paleta, que ficam abaixo disso em branco e em `neutral[50]`. Os tons 500 continuam valendo para o que não é texto (bordas, ícones, pontos decorativos, placeholder), onde o mínimo é 3:1 ou não se aplica. Ao escolher uma cor de texto fora de `semanticColors`, prefira os 700.

### Notas sobre a configuração do TypeScript

- `verbatimModuleSyntax: true` (`tsconfig.app.json`) — imports/exports somente de tipo devem usar `import type` / `export type` explicitamente; imports mistos falharão na compilação.
- `erasableSyntaxOnly: true` — evite sintaxe do TS que exija transformação em runtime (ex.: enums, parameter properties, namespaces).
- `noUnusedLocals` / `noUnusedParameters` estão habilitados — bindings não usados quebram o build, não só o lint.
- **O path alias `@/*` mapeia para `src/*`** — configurado tanto em `tsconfig.app.json` (`paths`, sem `baseUrl`; obsoleto nesta versão do TS) quanto em `vite.config.ts` (`resolve.alias`, via `path.resolve(import.meta.dirname, "src")`). Os dois devem permanecer sincronizados — o TS só faz a checagem de tipos do alias, é o Vite quem de fato o resolve em build/dev/test.
- Use `@/...` para imports transversais (ex.: `@/foundation`, `@/styles/GlobalStyle`) para evitar cadeias no estilo `../../../` conforme os componentes se aninham mais fundo nas camadas do Atomic Design. Mantenha imports relativos simples (`./Text.styles`) para arquivos co-localizados na mesma pasta de componente — o alias é para cruzar para uma preocupação de nível superior diferente, não para arquivos irmãos.
- **Cada bloco de `compilerOptions` em `tsconfig.app.json` deve ter suas chaves organizadas em ordem alfabética.** O arquivo já é dividido em blocos por comentário (`/* Bundler mode */`, `/* Linting */`, e o bloco inicial sem comentário) — a ordem alfabética se aplica dentro de cada bloco, não ao arquivo inteiro. Não é imposto por lint (JSON com comentários não é coberto pelo `eslint-plugin-perfectionist`) — revise manualmente.

### Convenções de ESLint/Prettier

- **Todo nome no código é em inglês**: pastas, arquivos, componentes, tipos, campos, variáveis, chaves de i18n e de rota e códigos de valores (ex.: `ACTIVE`/`INACTIVE`, `PRIVATE`, não `ATIVA`/`PRIVADA`), inclusive nas stories e testes. Em português ficam só o texto que aparece na tela (os catálogos de `src/i18n/locales/`, o conteúdo de exemplo das stories e dos mocks, e o texto que os testes procuram na tela), a documentação, e nomes de APIs de terceiros (`bairro`/`localidade`/`uf` do ViaCEP) ou siglas brasileiras sem equivalente (`cep`, `cpf`).
- A ordem dos imports é imposta pelo `eslint-plugin-simple-import-sort` (`simple-import-sort/imports` e `/exports` são `error`, não warnings) — deixe o `lint:fix` ou uma integração do editor ordenar os imports, em vez de ordená-los manualmente.
- Configuração do Prettier (`.prettierrc`): sem ponto e vírgula, aspas duplas, trailing commas em todo lugar, largura de impressão de 120, quebras de linha LF.
- **Arrow functions são preferidas em todo lugar** — imposto via `func-style: ["error", "expression", { allowArrowFunctions: true }]` (proíbe declarações `function foo() {}`) e `prefer-arrow-callback: "error"` (proíbe expressões `function` passadas como callback, ex.: `arr.map(function (x) {...})`). Sempre escreva `const foo = () => {...}`, inclusive para componentes (ver `Text.tsx`) e hooks.
- **Nunca use ternários aninhados.** Quando mais de uma condição precisa ser resolvida, use cadeias `if/else` ou early returns em vez disso. Um único ternário (`a ? b : c`) está ok; aninhar outro dentro dos ramos não está.
- **Nunca desestruture parâmetros de função inline.** Receba o `props` completo (ou outro argumento único) e desestruture-o na primeira linha do corpo: `const { a, b } = props`, não `({ a, b }: Props) => {}`. Isso vale tanto para componentes quanto para funções simples, incluindo callbacks de interpolação do `styled-components` (ver `Text.styles.ts`, onde o objeto de props inteiro é desestruturado uma vez dentro do corpo da função de interpolação, em vez de na sua lista de parâmetros). Não é imposto por lint no momento — nenhuma regra do ESLint cobre isso, então revise manualmente.
- **Prefira `async`/`await` a cadeias `.then()`/`.catch()`.** Escreva `const data = await getAddressByCep(cep)` dentro de uma função `async`, em vez de `getAddressByCep(cep).then(setData)`. Não é imposto por lint — revise manualmente.
- **Prefira `try`/`catch` a `.catch()` para tratamento de erro**, uma vez que a função que chama seja `async` (ver a regra anterior) — envolva o `await` em `try`/`catch` em vez de encadear `.catch()` na promise. Note que um callback de `useEffect` não pode ser `async` (seu valor de retorno é reservado para uma função de cleanup opcional), então quando um effect precisa dar `await` em algo, declare uma função `async` separada dentro do effect e a chame, em vez de tornar o callback do effect `async` ou cair para `.then()`/`.catch()` — ver `Experimental.tsx`.
- **Ordem alfabética de propriedades, obrigatórias antes de opcionais**, imposta pelo `eslint-plugin-perfectionist`, mas restrita a `files: ["src/ds-components/**/*.{ts,tsx}", "src/components/**/*.{ts,tsx}"]` (ver `eslint.config.js`) — deliberadamente **não** aplicada a `src/foundation/`, cujas escalas de token (`xs`→`4xl`, `50`→`900`) são ordenadas por tamanho, não alfabeticamente:
  - `perfectionist/sort-object-types` ordena os membros de tipos de prop (`type FooProps = {...}`) alfabeticamente dentro de dois grupos, nesta ordem: `required-property` primeiro, depois `optional-property` (cada grupo alfabético dentro de si — ver `TextProps`/`StyledTextProps`).
  - `perfectionist/sort-objects` ordena object literals e padrões desestruturados (ex.: `const { a, b } = props`) de forma puramente alfabética — não há conceito de obrigatório/opcional no nível da desestruturação.
- **As propriedades de `interface` e `type` devem estar em ordem alfabética em todo o projeto**, não só onde o `perfectionist` já impõe isso via lint (`src/ds-components/`/`src/components/`, acima). Fora desse escopo (ex.: `src/models/`, `src/utils/`, `src/pages/`) não é imposto por lint — revise manualmente. Ver `ViaCepAddress` em `src/models/viaCep/viaCep.ts` e `ParsedDate`/`FormatDateOptions` em `src/utils/dates/dates.ts` como exemplos já conformes.
- **Os blocos `scripts`, `dependencies` e `devDependencies` em `package.json` devem estar em ordem alfabética.** Não é imposto por lint (`perfectionist` não cobre arquivos `.json`) — revise manualmente ao adicionar, renomear ou remover um script/dependência.

## Ordenação do corpo do componente

Dentro de um componente, as constantes devem seguir esta sequência (quando cada tipo estiver presente), com cada bloco separado por exatamente uma linha em branco:

1. Chamadas de **`useRef`**
2. **Hooks customizados** (ex.: `useTooltip`, qualquer hook de `src/ds-components` ou de uma pasta `hooks/` compartilhada)
3. Chamadas de **`useState`**
4. **Constantes derivadas** (booleanos e outros valores calculados a partir de props/state)

A desestruturação de props que abre o corpo da função não conta como um bloco — a primeira linha em branco aparece depois dela, antes de qualquer que seja o bloco que vier primeiro. Uma linha em branco também segue o último bloco, antes do `return`.

```tsx
export const Example = (props: ExampleProps) => {
  const { disabled, label, tooltip } = props

  const inputRef = useRef<HTMLInputElement>(null)

  const { tooltipElement, tooltipHandlers } = useTooltip(tooltip)

  const [open, setOpen] = useState(false)

  const isActive = open && !disabled

  return (...)
}
```

## Regras específicas do React

- O `eslint-plugin-react-refresh` é configurado com o preset do Vite, que habilita `react-refresh/only-export-components`. **Um arquivo que exporta um componente React deve exportar apenas componentes** (mais, opcionalmente, constantes usadas puramente em padrões seguros para fast refresh, como `displayName`) — não adicione hooks, funções utilitárias ou constantes que não sejam componentes no mesmo arquivo de um componente, ou o Fast Refresh quebra e o lint vai apontar. Coloque hooks/utils compartilhados em seu próprio arquivo.
- As regras recomendadas do `eslint-plugin-react-hooks` estão ativas via `reactHooks.configs.flat.recommended` (`eslint.config.js`) — na versão instalada (`^7.1.1`) esse preset vai além de `rules-of-hooks`/`exhaustive-deps` e também inclui as "React Compiler rules" (`set-state-in-effect`, `set-state-in-render`, `static-components`, `use-memo`, `refs`, `purity`, `immutability`, ...), todas como `error`. Trate qualquer aviso/erro dessas regras como bug real a corrigir, não para suprimir com um comentário de disable inline.
  - `set-state-in-effect` é a que mais aparece ao buscar dados no mount: ela sinaliza quando a função passada para `useEffect` chama (mesmo que indiretamente, via uma referência) um setter de `useState`. Uma função criada com `useCallback` fora do effect e apenas chamada de dentro dele **é** rastreada como "chama setState" e dispara a regra, mesmo que a chamada de setState só aconteça depois de um `await`. A forma que passa no lint é declarar a função de fetch **inline dentro do próprio corpo do `useEffect`** (não via `useCallback` externo) — ver `src/pages/MyOrganization/MyOrganization.tsx`, que usa esse padrão e aciona um refetch por meio de um "reload token" no array de dependências em vez de chamar a função de fetch diretamente a partir de um handler de clique.
- Apenas componentes de função, sem componentes de classe — alinhado com o código existente e com a configuração de ESLint baseada em hooks.
- `react/prop-types` está desligado e não há validação de props em runtime — as props devem ser tipadas com interfaces/types do TypeScript, já que essa é a única camada de segurança de tipos para os contratos de componente.

## Convenções de Git

- As mensagens de commit seguem **Conventional Commits**: prefixe o assunto com um tipo (`feat:`, `fix:`, `docs:`, `refactor:`, `chore:`, `test:`, `style:`, `perf:`, `build:`, `ci:`, `revert:`, opcionalmente `type(scope):`) dependendo da mudança (ex.: `feat: add Text atom`, `fix: correct zIndex layer gaps`).
- Mantenha a **primeira linha com menos de 72 caracteres**. Coloque qualquer detalhe adicional no corpo do commit depois de uma linha em branco, em vez de deixar o assunto ficar longo demais.
- **Sempre execute `bun run test` antes de commitar** — nunca commite com a suíte de testes falhando.
- **O trabalho entra por Pull Request, nunca por push direto no `master`**: crie uma branch (`feat/...`, `fix/...`, `ci/...`), faça os commits nela, dê push e abra o PR. O merge no `master` é o que publica (ver abaixo).
- **O repositório só aceita squash merge**, e o commit gerado no `master` leva sempre o **título do PR** (mais ` (#<número>)`), com as mensagens dos commits do PR no corpo. Por isso **o título do PR segue o Conventional Commits** como uma mensagem de commit (ex.: `fix: keep the ColorPicker popover on screen`), e cabe nos 72 caracteres já com o sufixo — a checagem `pr-title` (ver abaixo) barra o merge quando não segue.

### CI/CD com GitHub Actions

**O app é publicado pelo Render, e o Storybook pelo Firebase Hosting.** O app é um Static Site do Render declarado no `render.yaml` (Blueprint): o próprio Render faz o build a partir do `master` (`bun install --frozen-lockfile && bun run build`, publicando `dist/`, com o rewrite de toda rota para `/index.html`), mas só depois de os checks do GitHub passarem no commit (`autoDeployTrigger: checksPass`), então um merge que quebra a esteira não é publicado. O site é o "School Flow 360 Frontend" (`https://school-flow-360-i2m0.onrender.com`; o sufixo do endereço veio do Blueprint que o criou), no ambiente Production do projeto do Render, junto do backend, e PR não ganha site de preview do app: um PR é revisado rodando o projeto localmente. **O `render.yaml` é a referência da configuração, mas nenhum Blueprint gerencia o site**: mudar a configuração é mudar o `render.yaml` e repetir a mudança no painel do Render. O build do app também roda na esteira (job `checks`), como checagem.

`.github/workflows/ci.yml` é a esteira única, com três jobs:

- **`checks`** — em todo PR e todo push no `master`: `bun install --frozen-lockfile`, lint, `format:check`, `tsc -b`, testes unitários, build do app, build do Storybook e o E2E do Playwright (com 3 workers, contra o próprio build em modo de desenvolvimento; o relatório fica como artefato quando algo falha). O build do Storybook vira artefato, então o Storybook publicado é exatamente o que foi testado. É a checagem exigida pela proteção do `master`: um PR só entra com ela verde, e é ela que libera o deploy do app no Render.
- **`preview`** — só em PR (e não de forks, que não recebem os secrets): publica o Storybook num canal de preview do Firebase, que vale 7 dias, e comenta o link no PR. O app não tem preview de PR.
- **`deploy`** — só em push no `master`, depois de `checks` passar: publica o Storybook no canal `live`. Se o GitHub perder o evento de um merge (nenhuma execução aparece para o commit no `master`), `gh workflow run ci.yml --ref master` roda a esteira à mão, com checks e deploy como num push. **Não rode `bun run deploy-storybook` no dia a dia** — publicar é fazer o merge; o script fica para uma emergência.

Um segundo workflow, `.github/workflows/pr-title.yml` (job **`pr-title`**), passa o **título do PR** pelo mesmo `commitlint` do hook `commit-msg`, já com o ` (#<número>)` que o squash merge acrescenta: é esse título que vira o commit no `master`, e nenhum hook local o vê. Fica separado da esteira para editar o título rodar só essa checagem. Também é exigido pela proteção do `master`.

A credencial do Storybook é o secret `FIREBASE_SERVICE_ACCOUNT_SCHOOL_FLOW_360_STORYBOOK`, uma conta de serviço criada pelo `firebase init hosting:github` com permissão só de Hosting; o app não precisa de secret na esteira, porque o Render lê o repositório direto. A versão do bun da esteira (`BUN_VERSION`) acompanha a usada localmente, e a do `render.yaml` acompanha a da esteira.

### Estas regras são impostas pelo Husky, não apenas documentadas

- `core.hooksPath` está definido como `.husky/_` (via `husky init`); o script `prepare` (`"prepare": "husky"`) refaz esse link a cada `bun install`, para que os hooks funcionem para qualquer pessoa que clone o repositório — não apague o script `prepare`.
- `.husky/pre-commit` executa `bunx lint-staged && bun run test` — o commit só chega a rodar a suíte de testes se o `lint-staged` passar, e é bloqueado se qualquer um dos dois falhar. `lint-staged.config.js` (na raiz) roda `eslint --fix` + `prettier --write` nos arquivos `.js`/`.jsx`/`.mjs`/`.cjs`/`.ts`/`.tsx` staged e só `prettier --write` em `.json`/`.css`/`.md`/`.html` staged — o `lint-staged` já re-adiciona ao stage os arquivos que ele corrigir.
- `.husky/commit-msg` executa `bunx commitlint --edit "$1"`, que rejeita o commit se a linha de assunto não seguir o formato `type:`/`type(scope):` do Conventional Commits ou exceder 72 caracteres. `commitlint.config.js` (na raiz) estende o preset `@commitlint/config-conventional` (que já traz a lista padrão de tipos — `feat`, `fix`, `docs`, `refactor`, `chore`, `test`, `style`, `perf`, `build`, `ci`, `revert`) e sobrescreve apenas `header-max-length` (72) — para restringir novamente a lista de tipos permitidos, adicione uma regra `type-enum` lá.
- Scripts Node-only (git hooks auxiliares, etc.) vão em `scripts/` e recebem um bloco dedicado no `eslint.config.js` com `globals.node` (para `process`, etc.) em vez do `globals.browser` usado em todo o resto — a pasta está vazia hoje (a validação de commit foi migrada para o `commitlint`), mas continua sendo o lugar certo para qualquer script Node futuro.
- Os arquivos de hook em `.husky/` devem manter o bit de execução (`100755`) no git, não `100644` — sistemas de arquivos do Windows não rastreiam isso nativamente, então depois de criar/editar um arquivo de hook, corrija-o explicitamente com `git update-index --chmod=+x .husky/<hook-name>` caso `git ls-files --stage .husky/<hook-name>` mostre `100644`.
